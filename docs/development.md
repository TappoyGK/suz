# ソースの開発規約

コンパイラ、ランタイム、スクリプトとテストの共通規約を定める。仕様文書の書き方は[仕様の執筆・レビュー基準](spec-writing.md)、PRの作成・レビューは[PRの作業手順](pr.md)、公開までの操作は[リリース手順](releasing.md)に従う。

## 配置・命名・責務

| 場所 | 置くもの |
|---|---|
| `compiler/src/` | Rustのコンパイラ・CLIと、その内部を直接検証する単体テスト |
| `compiler/tests/spec_cases/` | 公開API、CLI、生成C、環境層の振る舞いを確認するテスト |
| `compiler/tests/support/`・`compiler/tests/fixtures/` | テストの共通処理と入力データ |
| `runtime/` | 自作のCランタイムと環境層 |
| `runtime/third_party/` | 取得元・ライセンスを明記した外部コード |
| `scripts/` | 開発・検査・配布の操作に使うスクリプト |
| `docs/spec-cases/` | 読んで理解でき、継続してビルド・実行を検証するSuzの仕様例 |

Rustの関数・変数・モジュールは`snake_case`、型は`UpperCamelCase`、定数は`SCREAMING_SNAKE_CASE`で名付ける。Cのランタイムの外部シンボルには`suz_`を付ける。スクリプト名は同じ用途の既存ファイルに合わせ、単語をハイフンで区切る。

モジュールは責務ごとに分け、公開範囲は利用元が必要とする範囲に絞る。字句解析・構文解析・型検査・C生成・CLIのどこが判断を担当するかを決めてから実装する。同じ規則の判定や仕様の一覧を複数箇所に増やさない。

## コメントとrustdoc

コメント・rustdoc・Markdownの説明は日本語で書く。識別子、引用、外部コードの原文は書き換えない。

Rustのモジュールの冒頭には`//!`で責務と利用元を書く。処理が直接担当する主要な規則があれば規則IDを示す。関数や型の`///`には、名前や型だけでは分からない入力条件、返り値、状態の変更、失敗条件を説明する。利用元や関連項目を示すrustdocリンクは、実在する項目へ向ける。

処理中の`//`コメントには、判断の理由、不変条件、単位、評価順序、寿命など、コードだけから読み取れないことを書く。FFIや`unsafe`では、渡す領域・長さ・寿命・所有権など、安全に使える根拠を説明する。Cのヘッダーには、呼び出し側が守る条件と失敗時の扱いを書く。

コードの逐語訳、作業報告、レビューの会話、削除した実装の説明は残さない。設計上の理由と経緯をまとまって説明する場合は[設計記録](design.md)へ置き、ソースにはその箇所の理解に必要な理由を残す。

## ターミナル出力と診断

コマンドの出力、診断、テストの失敗メッセージは英語で書く。利用者が入力した文字列や、文字コードを検証するテストデータはそのまま扱う。

標準出力にはコマンドの結果を、標準エラーには診断や進捗を出す。集計スクリプトなど、出力を貼り付けたり別の処理へ渡したりするコマンドでは、標準出力に説明や進捗を混ぜない。SuzのCLIの出力先・診断形式・終了コードは[ツール仕様](tool.md)の「メッセージと終了」に従う。

診断は、何が不正か、対象の値や型、必要なら直し方を具体的に示す。ソースの診断には原因となった位置と規則IDを付け、関連する原因は関連診断で示す。Rustの診断は`diagnostic!`など既存の生成経路を使い、規則IDを表示文から解析し直さない。ライブラリ内部から直接ターミナルへ出力せず、診断を呼び出し元へ返す。

不正なSuzソースや外部ツールの失敗を、Rustの`panic!`・`unwrap()`で処理しない。内部で成立するはずの条件に`expect()`を使う場合は、成立するはずの条件が分かる文を書く。テストでは、前提となる準備や成功するはずの結果を確認するために`unwrap()`を使ってよい。

## テストの配置と書き方

### 単体テストの配置

簡易な行数集計で実装本体とテストを分けられるよう、次の配置を守る。集計のためにRustの構文を解析する処理は追加しない。

- テスト専用のRustファイルは`tests.rs`・`*_tests.rs`と名付けるか、`tests/`ディレクトリの下に置く。そこには通常ビルドで使う実装を置かない。
- 実装ファイル内のテスト本体、テスト専用の補助関数、テストモジュールの宣言は、通常の実装の後ろにまとめる。トップレベルで最初に現れる`#[cfg(test)]`の行から末尾までは、テスト専用とし、その後に通常の実装を置かない。
- トップレベルのテスト用属性は、行頭から`#[cfg(test)]`と書く。プラットフォームなどの追加条件は、次の行に別の`#[cfg(...)]`として書く。
- 本体内で必要になるテスト用の計測フックやフィールドは、その処理の場所に置ける。これらの少数の行は実装本体に含めて集計する。行数を厳密に分離するためだけに、処理を分割したり通常実行の処理を増やしたりしない。

### 検証する内容

既存の検証では検出できない誤動作を特定してから、テストを追加する。言語の受理・拒否・実行結果は仕様例集、内部の不変条件は単体テスト、CLI・Cとの連携・環境層はそれぞれの機能テストで確認する。同じ検証を場所を変えて増やさず、既存例への統合を優先する。

テスト名は確認する振る舞いが分かるものにし、入力は不具合を再現できる最小限のものにする。拒否のテストは失敗したことだけでなく、規則IDと必要な位置を確認する。実行テストは終了コードと必要な出力を確認し、結果を間違えた実装が通らないようにする。診断の文言そのものが検証対象の場合だけ、全文や具体的な文面を照合する。

生成Cの検査は、評価順序・余分な確保・呼び出し回数など、実行結果だけでは確認できない性質を対象にする。無関係な一時変数名や整形まで固定しない。

一時ファイルはテストごとの一時ディレクトリへ置き、終了時に片付ける。並列実行で衝突する固定パスや共有状態を使わない。共通の準備・Cビルド・実行には既存のテスト補助処理を使う。回数や順序で確認できる性質を、マシンの速度に依存する経過時間のしきい値で検査しない。

配布検査には、配布物の欠落や設置場所への依存など、配布固有の不具合を検出する検査だけを置く。追加する際は、その場所で検証する理由をコメントに書く。詳しい範囲は[リリース手順](releasing.md#配布検査)、例集の書式と通常・リリース検査の分担は[テスト基盤](../compiler/tests/README.md)を参照すること。

## 整形・リント・確認

Rustの版と利用する整形・リントツールは`rust-toolchain.toml`に従う。Rustはrustfmtで整形し、Clippyとrustdocの警告をエラーとして確認する。C・Python・シェルは、変更するファイルのインデントや命名に合わせる。外部コードへ自作コードの書式を一括適用しない。

```sh
cargo fmt --all -- --check
cargo clippy --locked --all-targets -- -D warnings
RUSTDOCFLAGS="-D warnings" cargo doc --locked --no-deps --document-private-items
cargo test --locked
git diff --check
```

作業中は変更に関係するテストで確認し、PRのCIでは通常テスト全体を実行する。リリース時は[リリース手順](releasing.md)に従って全検査を行う。文言や見出しだけの修正のために、振る舞いを変えないテストを追加しない。

リントの抑制には、必要な理由を近くのコメントに書き、適用範囲を必要最小限にする。新たな警告を消すために、プロジェクト全体へ一括で抑制を追加しない。
