# リリース手順

作業PRは `release/vVERSION` に集める。公開する変更が揃ったら、そのリリースブランチから `main` へリリースPRを作る。公開には、マージ後の `main` のコミットから生成・検証したバイナリを使う。

## 1. リリースブランチの作成

最新の `main` から `release/vVERSION` を作成してpushする。1つのリリースブランチに、複数の作業PRを取り込める。作業ブランチは取り込み先のリリースブランチから作成する。

`release/*` はPR経由で変更し、最新の取り込み先を反映した `work checks` の成功を必須とする。`main` はリリースPR経由で変更し、最新のmainを反映した `release checks` の成功を必須とする。両方の保護でforce pushとブランチ削除を禁止する。

## 2. 作業PR

### 仕様・実装・検証の照合

変更規則を、言語仕様・ランタイム仕様・ツール仕様と照合する。それぞれの規則について、実装と検証箇所を確認する。言語の振る舞いは仕様例集、環境層やメモリ管理はランタイム検証、引数や出力ファイルはCLI検証で確認する。既存の検証で確認できない振る舞いは、適切な検証先に追加する。

追加仕様を別文書にまとめた場合は、規則と例を正式な仕様・例集へ移し、検証を継続して実行できる状態にする。一時文書を削除しても、仕様や検証の根拠が失われないことを確認する。

仕様書と例集は、そのコミットの仕様を表す。表題や本文に現在のリリース番号を埋め込まず、過去の仕様はGitのリリースタグから参照する。

### コミット整理とPRの作成

作業PRは、単独でレビューできる変更単位にする。仕様・実装・テストと、それに必要な文書を含め、バージョンと変更履歴の確定はリリース準備で行う。

ブランチのコミットを、仕様・例・実装・その他の変更など、レビューできる意味のある単位に整理する。修正途中のコミットや作業記録だけのコミットはまとめる。コミットメッセージは、`docs:` などの接頭辞に続く説明を日本語で書く。

整理後に修正した場合は、変更内容に対応する既存のコミットへ取り込み、修正だけのコミットを残さない。複数の単位にまたがる修正は分けて取り込む。直前のコミットに属する修正はamendし、それ以前のコミットに属する修正はrebaseで該当コミットへまとめる。この整理は作業PRのマージ前に行う。リリースブランチへ取り込んだ履歴は書き換えない。

整理の前後でファイルの内容が変わっていないことを確認し、コミットごとの差分とPR全体の差分を確認する。内容も変更した場合は、その変更に必要な検査を再実行する。

作業ブランチをpushし、`release/vVERSION` 向けのPRを作成する。CIの結果と差分は人間が確認し、レビュー後にマージする。CIの成功だけでは自動マージしない。

イシューの修正は作業PRで関連付ける。リリースブランチ向けPRではGitHubの自動クローズを前提にせず、main向けのリリースPRに `Closes #番号` を記載する。

## 3. リリース準備とリリースPR

### バージョンと変更履歴

公開対象の作業PRを取り込んだ後、リリース準備用の作業ブランチでバージョンと変更履歴を確定し、リリースブランチ向けのPRとして取り込む。

バージョンは `compiler/Cargo.toml` で定め、Cargoで更新する `Cargo.lock`、`suz --version` の表示、変更履歴、公開するタグと一致させる。

[変更履歴](changelog.md)に、取り込んだPRの利用者向けの変更をまとめる。リンクや作業記録は含めず、変更内容を過去形で記述する。

### 全体の検査とレビュー

リリースブランチから `main` へPRを作成する。準備中はドラフトにし、作業PRをリリースブランチへ取り込むことで内容を更新する。

人間が差分と変更後の全体をレビューする。最新のmainをリリースブランチへ取り込む必要がある場合も、取り込み用の作業PRを使う。全検査と配布検査に成功した状態で、人間がリリースPRをマージする。修正が必要な場合は、リリースブランチ向けの作業PRを追加する。

### CIの実行条件

| 起動条件 | 必須チェック | 検査 |
|---|---|---|
| 作業PR → `release/*` | `work checks` | 書式、Clippy、通常テスト |
| `release/*` へのpush | `work checks` | 通常テスト。取り込んだ変更の組み合わせを検証する |
| リリースPR → `main` | `release checks` | 全検査、最適化別の仕様例集、サニタイザー、配布検査 |
| `main` へのpush | `release checks` | 全検査、配布検査、公開用成果物の保存 |
| 手動実行 | `release checks` | 選択したブランチで全検査と配布検査 |

作業ブランチへのpushではCIを起動せず、PRの検査と重複させない。大きな変更を取り込んだ段階では、手動で全検査を実行できる。

検査対象を絞る設定は使わない。CIの実行環境はワークフローで定め、OS・Rust・Clang・SDKのバージョンを実行ログで確認する。対応環境は[ツール仕様](tool.md)で管理する。

### 配布検査

リリース用バイナリをリポジトリ外へコピーし、単体での利用と `emit-c` の出力からのビルドを確認する。追加機能やオプションが、配布したバイナリと生成したCの両方で動作することを確認する。外部ツールがない場合の診断も確認する。

これらの確認は `scripts/test-distribution.py` に含める。追加機能に必要な検証が不足している場合は、この検査を更新する。

## 4. mainの再検査と成果物の取得

マージによる `main` へのpushで、CIが全検査と配布検査を再実行する。失敗した場合は公開を止め、修正を別のPRで行う。マージ済みのコミットがCIの失敗によって自動で取り消されることはない。

公開対象のコミットと一致する、成功した `main` のCI実行を選ぶ。Actionsの成果物 `suz-macos-arm64-COMMIT` をダウンロードし、中の `suz-macos-arm64.tar.gz` を展開する。

| ファイル | 内容 |
|---|---|
| `suz` | 検証済みの実行ファイル |
| `SHA256SUMS` | 実行ファイルのSHA-256 |
| `COMMIT` | ビルド元のコミットID |

展開したディレクトリで次を実行し、ハッシュ・バージョン・コミットIDを確認する。

```sh
shasum -a 256 -c SHA256SUMS
./suz --version
cat COMMIT
```

成果物の保存期間は30日とする。期限切れなどで再生成する場合は、対象コミットで全検査と配布検査を再実行する。

署名などで実行ファイルを書き換える場合は、その処理後に配布検査を実行し、SHA-256を更新する。公開するファイルそのものが検査に成功していることを条件とする。

## 5. タグと公開

検査に成功した `main` 上の公開対象コミットに `vVERSION` のタグを付け、pushする。タグの参照先と成果物の `COMMIT` が一致することを確認する。

そのタグからGitHub Releaseを作成し、対象OS・CPUを明示する。検証済みの `suz`、そのSHA-256、変更内容と検証環境を記したリリースノートを公開する。

## ローカルでの検査

Rustは `rust-toolchain.toml` に従う。Cコンパイラ・SDKとPython 3を用意し、リポジトリのルートで実行する。

```sh
./scripts/test-release.sh --locked
cargo build --release --locked -p suz
python3 scripts/test-distribution.py target/release/suz
```

配布検査は `compiler/Cargo.toml` から期待バージョンを取得する。別のバージョンを検査する場合は `--version VERSION` で明示する。`CARGO_TARGET_DIR` を変更している場合は、その配下の実行ファイルを指定する。
