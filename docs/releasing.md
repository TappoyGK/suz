# リリース手順

作業PRは `release/vVERSION` に集める。リリースブランチから `main` へのドラフトPRを早期に作り、作業PRの取り込みに合わせて更新する。最後の作業PRでバージョンと変更履歴を確定する。公開には、マージ後の `main` のコミットから生成・検証したバイナリを使う。

## 毎回の進め方

1. 最新の `main` からリリースブランチを作り、pushする。
2. mainとの差分ができた時点で、main向けのリリースPRをドラフトとして作る。差分がない間は作成できないため、最初の作業PRを取り込んだ直後に作成する。
3. 作業PRを1つのスタックにまとめ、Markdownファイルのみを変更するPR、それ以外のPR、リリース準備PRの順に並べる。PRの追加・更新・マージ時には、取り込み先と順序を同期する。
4. 公開対象が揃ったら、スタックの最後のリリース準備PRでバージョンと変更履歴を確定する。取り込む全作業PRと変更履歴を照合し、利用者向けの変更が欠けていないことを確認する。
5. 準備PRを取り込んだら、リリースPRのタイトル・説明・関連イシューを確定し、ドラフトを解除する。人間がレビューとCIの結果確認を行い、merge commitでmainへ取り込む。
6. マージ後のmainのコミットに対応する検証済み成果物からタグとGitHub Releaseを公開する。

## 1. リリースブランチの作成

最新の `main` から `release/vVERSION` を作成してpushする。1つのリリースブランチに、複数の作業PRを取り込める。作業ブランチは取り込み先のリリースブランチから作成する。

mainとの差分ができたら、次のコマンドでドラフトのリリースPRを作成する。説明は実際の改行を持つファイルに用意する。既存のリリースPRがある場合は、それを更新する。

```sh
gh pr create --base main --head release/vVERSION --draft \
    --title "release: vVERSION" --body-file /path/to/release-pr.md
```

`release/*` はPR経由で変更し、最新の取り込み先を反映した `work checks` の成功を必須とする。`main` はリリースPR経由で変更し、最新のmainを反映した `release checks` の成功を必須とする。両方の保護でforce pushとブランチ削除を禁止する。

## 2. 作業PR

### 仕様・実装・検証の照合

変更規則を、言語仕様・ランタイム仕様・ツール仕様と照合する。それぞれの規則について、実装と検証箇所を確認する。言語の振る舞いは仕様例集、環境層やメモリ管理はランタイム検証、引数や出力ファイルはCLI検証で確認する。既存の検証で確認できない振る舞いは、適切な検証先に追加する。

追加仕様を別文書にまとめた場合は、規則と例を正式な仕様・例集へ移し、検証を継続して実行できる状態にする。一時文書を削除しても、仕様や検証の根拠が失われないことを確認する。

仕様書と例集は、そのコミットの仕様を表す。表題や本文に現在のリリース番号を埋め込まず、過去の仕様はGitのリリースタグから参照する。

### コミットとレビュー対応

作業PRは、単独でレビューできる変更単位にする。仕様・実装・テストと、それに必要な文書を含め、バージョンと変更履歴の確定はリリース準備で行う。

レビューで見つかった変更も、対象のイシューと関係するものだけをそのPRで扱う。無関係な運用変更や別の問題は独立した作業PRに分ける。

PRを作成する前に、差分が単独でレビューできる内容になっていることを確認する。コミットメッセージは、`docs:` などの接頭辞に続く説明を日本語で書く。

レビュー対応は追加コミットとして残す。既存コミットへのamendやsquashは行わず、レビュー後に何を直したかを差分で追える状態にする。スタックの下段を反映するためのrebaseでは、各レビュー対応コミットの内容と区切りを維持する。

作業PRをマージする時にsquashし、1つの作業PRを1つの意味のあるコミットにまとめる。人間が変更全体とレビュー対応を確認してからマージする。リリースブランチへ取り込んだ履歴は書き換えない。

独立した作業ブランチをpushし、`release/vVERSION` 向けのPRを作成する。CIの結果と差分は人間が確認し、レビュー後にマージする。CIの成功だけでは自動マージしない。

イシューの修正は作業PRで関連付ける。リリースブランチ向けPRではGitHubの自動クローズを前提にせず、main向けのリリースPRに `Closes #番号` を記載する。

### 作業PRのスタック

同じリリースに直接取り込む作業PRと、後述するイシューの集約PRは、1つのGitHubスタックで管理する。スタックの基点を `release/vVERSION` とし、Markdownファイルのみを変更するPR、それ以外のPR、リリース準備PRの順に積む。Markdownのみかどうかは、そのPR自身の変更ファイルで判断する。同じ区分では基本ルールの変更を先に置き、依存する変更は依存先より後に置く。main向けのリリースPRはこのスタックに含めない。

GitHub CLIの公式拡張 `github/gh-stack` を使う。既存のブランチを採用する場合は、各ブランチを直下のブランチの上へ載せ替え、下から順に指定する。

```sh
gh extension install github/gh-stack
gh stack init --base release/vVERSION rules changes prepare
gh stack submit
```

リリース準備のPRは最後に置く。途中に作業を追加する場合は `gh stack modify` で準備PRの前にブランチを挿入し、`gh stack submit` でpushとPRの関連付けを更新する。下段を修正した場合は `gh stack rebase` と `gh stack push` で上段にも反映する。スタック内の各PRは、直下のブランチとの差分としてレビューする。

PRの作成・追加・更新時と、下段のPRがマージされた後は、公開中のPR一覧とスタックを照合し、次を確認する。

- 同じリリースに直接取り込む作業PRとイシューの集約PRが、ドラフトや運用変更のPRも含めて、すべてスタックに入っている。
- Markdownファイルのみを変更するPRを、それ以外のPRより先に置いている。同じ区分では基本ルールの変更と依存関係に従って並べている。リリース準備のPRは最後に置いている。
- 最下段の作業PRはリリースブランチを、それ以外は直下の未マージの作業ブランチを取り込み先にしている。各PRの差分には、そのPRの変更だけが含まれている。
- GitHub上のスタックの順序・取り込み先と、ローカルのブランチの親子関係・スタック情報が一致している。

PRを作成しただけで作業を終えず、スタックへの組み込みと順序の確認まで行う。下段のマージ後は `gh stack sync` で同期する。載せ替えによって公開済みの履歴を更新する場合は、その理由を伝え、`--force-with-lease` を使う。レビュー対応のコミットは載せ替え時にもまとめない。

スタックの保護ルールとCIは、その基点に従う。ワークフローのジョブ判定でも `github.event.pull_request.stack.base.ref` を使い、スタック外では通常のPRのマージ先を使う。CIの結果確認とマージは人間が行う。

### 複数の段階に分かれるイシュー

複数の作業PRをまとめて取り込むイシューでは、最新のリリースブランチから `issue/番号-内容` を作る。段階ごとの作業ブランチは、このイシューブランチを基点とする別のスタックに積む。

```text
release/vVERSION
└ issue/番号-内容
  └ 段階1の作業ブランチ
    └ 段階2の作業ブランチ
```

最下段の作業PRはイシューブランチを、それ以外は直下の未マージの作業ブランチを取り込み先にする。各PRには、その段階の変更だけを含める。MarkdownのみのPRの優先、依存関係の順序、レビュー対応コミットの維持は、通常の作業スタックと同じとする。

```sh
gh stack init --base issue/番号-内容 stage1 stage2
gh stack submit
```

段階ごとの作業PRは人間がレビューしてsquash mergeする。下段を取り込んだら `gh stack sync` で上段の取り込み先と履歴を同期する。

イシューブランチに最初の変更を取り込んだ時点で、リリースブランチ向けの集約PRをドラフトとして作る。差分のない集約PRを作るためだけの空コミットは作らない。集約PRはリリース側のスタックに含め、段階ごとの作業スタックには含めない。リリース側にも先行する未マージのPRがある場合は、通常のスタックと同じく直下のブランチを取り込み先にする。

必要な段階を取り込んだら、集約PRの説明を最終的な変更内容に更新してドラフトを解除する。人間が確認し、段階ごとのコミットを保つためmerge commitで取り込む。PR一覧を確認するときは、リリース側とイシュー側の両方のスタックを照合し、各PRがどちらか一方に属していることを確認する。

#### リリースブランチの更新を反映する

リリースブランチが進んだ場合は、イシューブランチから同期用の作業ブランチを作り、最新のリリースブランチをmergeする。衝突は同期用ブランチで解消し、関連する検査を実行する。解消内容をPRに記載し、人間が確認してからイシューブランチへmerge commitで取り込む。同期用PRはイシュー側のスタックの最下段に置き、既存の作業ブランチをその上へ載せ替える。

この同期ではリリースブランチの履歴を保持するため、squashしない。イシューブランチへ取り込み済みの段階の履歴は書き換えない。同期用PRのマージ後は、残る作業ブランチを更新後のイシューブランチへ載せ替え、各PRにその段階の差分だけが残ることを確認する。衝突の解消に仕様や動作の判断が必要な場合は、その変更をPRに明記してレビュー対象とする。

#### 次のリリースへ持ち越す

イシュー全体を持ち越す場合は、集約PRをドラフトのまま維持する。次のリリースブランチを作成した後、その更新を前項の同期用PRでイシューブランチへ取り込む。集約PRを次のリリース側のスタックへ移し、取り込み先・説明・関連イシューを更新する。段階ごとの作業スタックは同じイシューブランチを基点として継続する。

完了した段階だけを今回のリリースに含める場合は、取り込みを区切り、イシューブランチに入っている変更だけで公開可能か確認する。未完成の変更を含んでいる場合は、そのまま集約PRをマージしない。公開可能な段階までの集約PRを人間がマージした後、次のリリースブランチから新しいイシューブランチを作る。名前には `issue/番号-内容-2` などの継続番号を付ける。

未マージの作業ブランチは新しいイシューブランチへ載せ替え、既に公開対象に含めたコミットを再び差分に含めない。新しい基点で段階ごとのスタックを作り直し、PRの取り込み先を更新する。最初の段階を取り込んだ時点で、新しい集約PRをドラフトとして作る。イシューが完了していない間は、リリースPRにそのイシューの `Closes` を記載しない。

いずれの場合も、移動後にリリース側とイシュー側のスタックを照合する。履歴の載せ替えは理由を伝えたうえで `--force-with-lease` を使い、レビュー対応コミットの区切りを保つ。

## 3. リリース準備とリリースPR

### バージョンと変更履歴

リリース準備PRは、そのリリースで最後に取り込む作業PRとする。公開対象の作業PRを取り込んだ後、リリース準備用の作業ブランチでバージョンと変更履歴を確定し、リリースブランチ向けのPRとして取り込む。準備PRの後に変更が追加された場合は、準備PRをその上に載せ直して内容を更新する。

バージョンは `compiler/Cargo.toml` で定め、Cargoで更新する `Cargo.lock`、`suz --version` の表示、変更履歴、公開するタグと一致させる。

[変更履歴](changelog.md)に、取り込んだ全作業PRの利用者向けの変更をまとめる。PRの一覧と差分を照合し、機能追加・仕様変更・修正の記載漏れを確認する。リンクや作業記録は含めず、変更内容を過去形で記述する。

### 全体の検査とレビュー

作成済みのmain向けリリースPRは、準備中はドラフトを維持し、作業PRをリリースブランチへ取り込むことで差分を更新する。最後の準備PRを取り込んだ後、説明を確定した公開内容に書き直し、関連イシューの `Closes` を揃えてドラフトを解除する。古い取り込み順や準備中の記述を残さない。

人間が差分と変更後の全体をレビューする。最新のmainをリリースブランチへ取り込む必要がある場合も、取り込み用の作業PRを使う。全検査と配布検査に成功した状態で、人間がリリースPRをマージする。作業PR単位のコミットを保つため、リリースPRにはmerge commitを使う。修正が必要な場合は、リリースブランチ向けの作業PRを追加する。

### CIの実行条件

| 起動条件 | 必須チェック | 検査 |
|---|---|---|
| 作業PR → `release/*` | `work checks` | 書式、Clippy、通常テスト |
| `release/*` へのpush | `work checks` | 通常テスト。取り込んだ変更の組み合わせを検証する |
| リリースPR → `main` | `release checks` | 全検査、最適化別の仕様例集、サニタイザー、配布検査 |
| `main` へのpush | `release checks` | 全検査、配布検査、公開用成果物の保存 |
| 手動実行 | `release checks` | 選択したブランチで全検査と配布検査 |

作業ブランチへのpushではCIを起動せず、PRの検査と重複させない。大きな変更を取り込んだ段階では、手動で全検査を実行できる。

Markdown文書だけの変更では、変更ファイルの判定だけを行い、ビルド・テスト・配布物の生成を省略する。ただし、検証に使う `docs/spec.md`、`docs/spec-cases.md`、`docs/spec-cases/` 配下と、バイナリに埋め込む `runtime/third_party/ryu/README.md` の変更では検査を実行する。手動実行では全検査、リリースブランチの新規作成時は通常テストを行う。変更の判定に失敗した場合は必須チェックを失敗させる。

ワークフロー全体はパス条件で省略せず、必須チェックのジョブを条件付きで省略する。これにより、文書だけのPRでも必須チェックが未完了のまま残らない。新たに文書をビルドや検証の入力にする場合は、`scripts/ci-changes.py` の判定とテストも更新する。

検査を実行する場合は、検査対象を絞る設定は使わない。CIの実行環境はワークフローで定め、OS・Rust・Clang・SDKのバージョンを実行ログで確認する。対応環境は[ツール仕様](tool.md)で管理する。

### 配布検査

リリース用バイナリをリポジトリ外へコピーし、単体での利用と `emit-c` の出力からのビルドを確認する。追加機能やオプションが、配布したバイナリと生成したCの両方で動作することを確認する。外部ツールがない場合の診断も確認する。

これらの確認は `scripts/test-distribution.py` に含める。追加機能に必要な検証が不足している場合は、この検査を更新する。

## 4. mainの再検査と成果物の取得

マージによる `main` へのpushで、CIが全検査と配布検査を再実行する。失敗した場合は公開を止め、修正を別のPRで行う。マージ済みのコミットがCIの失敗によって自動で取り消されることはない。

公開対象のコミットと一致する、成功した `main` のCI実行を選ぶ。Actionsの成果物 `suz-macos-arm64-COMMIT` をダウンロードし、中の `suz-macos-arm64.tar.gz` を展開する。

| ファイル | 内容 |
|---|---|
| `suz` | 検証済みの実行ファイル |
| `SHA256SUMS` | 実行ファイルのSHA-256 |
| `COMMIT` | ビルド元のコミットID |

展開したディレクトリで次を実行し、ハッシュ・バージョン・コミットIDを確認する。

```sh
shasum -a 256 -c SHA256SUMS
./suz --version
cat COMMIT
```

成果物の保存期間は30日とする。期限切れなどで再生成する場合は、対象コミットで全検査と配布検査を再実行する。

署名などで実行ファイルを書き換える場合は、その処理後に配布検査を実行し、SHA-256を更新する。公開するファイルそのものが検査に成功していることを条件とする。

## 5. タグと公開

検査に成功した `main` 上の公開対象コミットに `vVERSION` のタグを付け、pushする。タグの参照先と成果物の `COMMIT` が一致することを確認する。

そのタグからGitHub Releaseを作成し、対象OS・CPUを明示する。検証済みの `suz`、そのSHA-256、変更内容と検証環境を記したリリースノートを公開する。

## ローカルでの検査

Rustは `rust-toolchain.toml` に従う。Cコンパイラ・SDKとPython 3を用意し、リポジトリのルートで実行する。

```sh
./scripts/test-release.sh --locked
cargo build --release --locked -p suz
python3 scripts/test-distribution.py target/release/suz
```

配布検査は `compiler/Cargo.toml` から期待バージョンを取得する。別のバージョンを検査する場合は `--version VERSION` で明示する。`CARGO_TARGET_DIR` を変更している場合は、その配下の実行ファイルを指定する。
