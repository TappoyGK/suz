# リリース手順

作業PRは `release/vVERSION` に集める。リリースブランチから `main` へのドラフトPRを早期に作り、作業PRの取り込みに合わせて更新する。最後のリリース準備PRでバージョンと変更履歴を確定する。公開には、マージ後の `main` のコミットから生成・検証したバイナリを使う。PRの区分は[PRの種類](pr.md#prの種類)を参照する。

## 毎回の進め方

1. 最新の `main` からリリースブランチを作り、pushする。
2. mainとの差分ができた時点で、main向けのリリースPRをドラフトとして作る。差分がない間は作成できないため、最初の作業PRを取り込んだ直後に作成する。
3. [PRの作業手順](pr.md)に従って作業PRを取り込む。
4. 公開対象が揃ったら、スタックの最後のリリース準備PRでバージョンと変更履歴を確定する。取り込む全作業PRと変更履歴を照合し、利用者向けの変更が欠けていないことを確認する。
5. 準備PRを取り込んだら、リリースPRのタイトル・説明・関連イシューを確定し、ドラフトを解除する。人間がレビューとCIの結果確認を行い、merge commitでmainへ取り込む。
6. マージ後のmainのコミットに対応する検証済み成果物からタグとGitHub Releaseを公開する。
7. HomebrewのFormulaを更新し、インストールと検査の成功を確認してtapへpushする。GitHub ReleaseとHomebrewの両方が更新されたことを確認して完了とする。

## 1. リリースブランチの作成

最新の `main` から `release/vVERSION` を作成してpushする。1つのリリースブランチに、複数の作業PRを取り込める。

mainとの差分ができたら、次のコマンドでドラフトのリリースPRを作成する。説明は実際の改行を持つファイルに用意する。既存のリリースPRがある場合は、それを更新する。

```sh
gh pr create --base main --head release/vVERSION --draft \
    --title "release: vVERSION" --body-file /path/to/release-pr.md
```

### ブランチ保護

`release/*` はPR経由で変更し、最新の取り込み先を反映した `work checks` の成功を必須とする。`main` はリリースPR経由で変更し、最新のmainを反映した `release checks` の成功を必須とする。両方の保護でforce pushとブランチ削除を禁止する。

## 2. 作業PRの取り込み

作業PRの作成・レビュー・スタック管理・CIの確認は[PRの作業手順](pr.md)に従う。

## 3. リリース準備とリリースPR

### バージョンと変更履歴

リリース準備PRは、そのリリースで `release/*` に最後に取り込むPRとする。公開対象の作業PRを取り込んだ後、リリース準備用のブランチでバージョンと変更履歴を確定する。[作業PRのスタック](pr.md#作業prのスタック)と同じ操作でスタックの最後に積み、準備PRの後に変更が追加された場合は、その上に載せ直して内容を更新する。コミット・レビュー・マージは[コミットとレビュー対応](pr.md#コミットとレビュー対応)、CIは[CIの確認](pr.md#ciの確認)に従う。

バージョンは `compiler/Cargo.toml` で定め、Cargoで更新する `Cargo.lock`、`suz --version` の表示、変更履歴、公開するタグと一致させる。

[変更履歴](changelog.md)に、取り込んだ全作業PRの利用者向けの変更をまとめる。PRの一覧と差分を照合し、機能追加・仕様変更・修正の記載漏れを確認する。各項目に対応するイシューとPRのリンクを添え、変更内容を過去形で記述する。作業記録は含めない。

### コード統計

変更履歴を更新するリリース準備PRと、main向けのリリースPRの本文に、公開対象の総行数と内訳を記載する。対象のソースをコミットした作業ツリーで、次を実行して出力の表を貼る。準備中にソースを変更した場合は数え直す。

```sh
python3 scripts/code-stats.py
```

Gitで追跡するファイルの現在の内容を、空行・コメントを含む物理行数で数える。集計対象は次のとおりとし、過去のタグとの比較や増減率は出さない。統計はそのリリースの規模を示す参考値であり、品質や開発成果の評価には使わない。

| 表の項目 | 対象 |
|---|---|
| Compiler implementation | `compiler/src/**/*.rs`から単体テスト分を除いた行数 |
| Compiler unit tests | `compiler/src/`内のテスト専用ファイルと、実装ファイル末尾のテスト部分 |
| Integration and spec tests | `compiler/tests/**/*.{rs,c}`。共通処理・入力データも含む |
| Runtime | `runtime/**/*.{c,h}`のうち`runtime/third_party/`以外 |
| Third-party code | `runtime/third_party/**/*.{c,h}` |
| Documentation | `docs/`直下のMarkdown文書 |
| Spec examples | `docs/spec-cases/`直下のMarkdown文書 |

単体テストの区分は[ソースの配置規約](development.md#単体テストの配置)に従う。Rustを解析して厳密に分類するのではなく、規約に合わせてソースを配置する。本体内のテスト用計測フックは実装本体に含める。集計結果の保存ファイルや統計専用のCIは設けない。

### 全体の検査とレビュー

作成済みのmain向けリリースPRは、準備中はドラフトを維持し、作業PRをリリースブランチへ取り込むことで差分を更新する。最後の準備PRを取り込んだ後、説明を確定した公開内容に書き直し、関連イシューの `Closes` を揃えてドラフトを解除する。古い取り込み順や準備中の記述を残さない。

人間が差分と変更後の全体をレビューする。最新のmainをリリースブランチへ取り込む必要がある場合も、取り込み用の作業PRを使う。全検査と配布検査に成功した状態で、人間がリリースPRをマージする。作業PR単位のコミットを保つため、リリースPRにはmerge commitを使う。修正が必要な場合は、リリースブランチ向けの作業PRを追加する。

### CIの実行条件

| 起動条件 | 必須チェック | 検査 |
|---|---|---|
| `release/*` へのpush | `work checks` | rustdoc、通常テスト。取り込んだ変更の組み合わせを検証する |
| リリースPR → `main` | `release checks` | 全検査、最適化別の仕様例集、サニタイザー、配布検査 |
| `main` へのpush | `release checks` | 全検査、配布検査、公開用成果物の保存 |
| 手動実行 | `release checks` | 選択したブランチで全検査と配布検査 |

手動実行ではMarkdownのみの変更でも全検査を行う。リリースブランチの新規作成時は検査を省略せず、通常テストを行う。

作業PRのCIと、Markdownのみの変更に対する検査省略などの共通条件は[PRの作業手順](pr.md#ciの確認)を参照する。大きな変更を取り込んだ段階では、手動で全検査を実行できる。

### 配布検査

リリース用バイナリをリポジトリ外へコピーし、単体での利用と `emit-c` の出力からのビルドを確認する。配布物の欠落、開発環境への依存、設置場所への依存を検出するため、最小限の入力プログラムを使う。

これらの確認は `scripts/test-distribution.py` に含める。言語仕様、診断、実行時の振る舞いなど、通常のテストで確認できる検査は追加しない。新機能の追加を理由に検査を増やさない。検査を追加する際は、配布固有のどの不具合を検出するのかをコメントに明記する。その理由を示せない検査は追加せず、既存の検査であれば削除する。

## 4. mainの再検査と成果物の取得

マージによる `main` へのpushで、CIが全検査と配布検査を再実行する。失敗した場合は公開を止め、修正を別のPRで行う。マージ済みのコミットがCIの失敗によって自動で取り消されることはない。

公開対象のコミットと一致する、成功した `main` のCI実行を選ぶ。Actionsの成果物 `suz-macos-arm64-COMMIT` をダウンロードし、中の `suz-macos-arm64.tar.gz` を展開する。

| ファイル | 内容 |
|---|---|
| `suz` | 検証済みの実行ファイル |
| `SHA256SUMS` | 実行ファイルのSHA-256 |
| `COMMIT` | ビルド元のコミットID |

展開したディレクトリで次を実行し、ハッシュ・バージョン・コミットIDを確認する。

```sh
shasum -a 256 -c SHA256SUMS
./suz --version
cat COMMIT
```

成果物の保存期間は30日とする。期限切れなどで再生成する場合は、対象コミットで全検査と配布検査を再実行する。

署名などで実行ファイルを書き換える場合は、その処理後に配布検査を実行し、SHA-256を更新する。公開するファイルそのものが検査に成功していることを条件とする。

## 5. タグと公開

検査に成功した `main` 上の公開対象コミットに `vVERSION` のタグを付け、pushする。タグの参照先と成果物の `COMMIT` が一致することを確認する。

そのタグからGitHub Releaseを作成し、対象OS・CPUを明示する。検証済みの `suz`、そのSHA-256、変更内容と検証環境を記したリリースノートを公開する。

## 6. Homebrewの更新

[Homebrew tap](https://github.com/TappoyGK/homebrew-tap) の `Formula/suz.rb` を更新する。URLを公開したバージョンの `suz-macos-arm64.tar.gz` に変更し、そのアーカイブのSHA-256を設定する。実行ファイルのハッシュを記載した `SHA256SUMS` の値とは区別する。

ローカルのtapで変更を適用し、次を実行する。

```sh
brew audit --strict tappoygk/tap/suz
brew reinstall tappoygk/tap/suz
brew test tappoygk/tap/suz
suz --version
```

公開した版のインストールと検査の成功を確認し、Formulaの変更をコミットしてtapへpushする。GitHub上のFormulaのURLとSHA-256が公開したアーカイブと一致していることを確認する。

## ローカルでの検査

Rustは `rust-toolchain.toml` に従う。Cコンパイラ・SDKとPython 3を用意し、リポジトリのルートで実行する。

```sh
./scripts/test-release.sh --locked
cargo build --release --locked -p suz
python3 scripts/test-distribution.py target/release/suz
```

配布検査は `compiler/Cargo.toml` から期待バージョンを取得する。別のバージョンを検査する場合は `--version VERSION` で明示する。`CARGO_TARGET_DIR` を変更している場合は、その配下の実行ファイルを指定する。
