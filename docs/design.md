# 設計記録

この文書は設計の理由と経緯を記録する。言語の規則は[言語仕様](spec.md)、実装の契約は[ランタイム仕様](runtime.md)を正本とする。記録の書き方は[仕様の執筆・レビュー基準](spec-writing.md)に従う。

## 関数の作用を扱う設計方針

[#135](https://github.com/TappoyGK/suz/issues/135)では、circuitや契約式など、特定の処理を禁止する場所を持つ機能に向けて、作用の検査の方針を決めた。以下は今後の機能の設計方針であり、具体的な構文や受理・拒否の規則は、それを使う機能の言語仕様で定める。

### 関数の宣言を増やさずに検査する

作用を制限するために、関数ごとに`pure fn`・`noalloc fn`・`noio fn`のような修飾子を書かせる設計を基本としない。利用する場所で必要な制限に合わせて、コンパイラが関数本体と呼び出し先を解析する。補助関数やライブラリを、利用する場所ごとに書き分ける負担を避けるためである。

解析した情報はコンパイラ内部で共用する。関数の宣言や型を区別することと、内部で要約情報を持つことは別である。IRに付けるか、別の解析用の表に保存するかは実装時に決める。

まず扱う情報は、環境層の確保を呼びうることと、出力を行いうることとする。解析する情報と、各機能が禁止する処理を分け、分類はこの2つに限定しない。分類を追加するときは、先に言語仕様の該当する規則と`execution.cost-resources`に従う各操作の表へ記載する。外部処理については表の「外部処理」に記載し、利用者向けの説明とコンパイラの解析を一致させる。具体的な伝播方法と検査は、最初にその情報を使う機能と合わせて実装する。

### 外部関数の契約を信頼する

外部関数の作用は、プログラマーがextern宣言に明示した契約を信頼して検査する。ポインタの保持については、Cが呼び出し後もポインタを保持できることを明示する`keep`がある（言語仕様の`ffi.keep`）。確保や出力についても、必要な契約を宣言する方法を、その契約を使う検査と合わせて定める。

extern関数であること自体を拒否理由にせず、Cの内部の正しさをSuzが証明することも求めない。一方、`trusted`だけから「確保しない」「出力しない」という個別の契約は推定しない。宣言されていない作用は、行いうるものとして扱う。

### 能力の引数渡しはライブラリごとに選ぶ

ファイルやネットワークを扱うためのオブジェクトを引数として渡す設計は、言語や標準ライブラリ全体の義務にしない。依存関係の明示やテスト時の差し替えには役立つが、FFIなどの別経路があるため、引数型だけでは外部アクセスの不在を表せない。必要なライブラリで選べる設計とする。

### ログで調べたい動作を変えないための制約

例えば、音声を生成する処理で音切れの原因を調べるためにログを入れたところ、そのログの出力待ちで音切れが起きたら、元の問題を調べにくくなる。

そのため、出力待ちを禁止する音声処理では、ログも禁止する。ログを無効にする設定でも、そのコードは受け付けない。有効に切り替えたときに、音切れの原因を持ち込めてしまうからである。作用の検査では、除外されるログも出力操作として扱い、埋め込み式も検査する。例えば、確保を禁止する場所では、埋め込み式による確保も禁止する。

こうした場所では、処理時間を一定に抑えられることをプログラマー自身が確認できる記録方法を使う。例えば、あらかじめ確保したメモリ上のリングバッファに固定長のデータを書き込み、表示やファイルへの出力は音声処理の外で行う。バッファが満杯になっても、空きを待ったり追加のメモリを確保したりしない方法にする。

## 寿命検査の前提を明記した経緯

言語仕様の`arena.soundness-premise`は、[rust-lang/rust#164250](https://github.com/rust-lang/rust/issues/164250)を受けて明記した。報告されたRustの例では、フィールドへの代入を通じて寿命の制約を満たさない値が入り、デストラクタがその値を大域の保存先へ移すことで、寿命を終えた値への参照が残った。

Suzでは、回収時に利用者のコードを実行しないこと、書き換え可能な大域の保存先を持たないこと、寿命やnull許容性の変位を認めないことを、寿命検査の前提にしている。ただし、機能が少ないために避けられている組み合わせもある。現在の制約を緩める機能は、単独の性質だけでなく、保存・返却・コールバック・回収との組み合わせを検討する必要がある。

前提そのものは[言語仕様の寿命検査の前提](spec.md#93-寿命検査の前提)、変更時の検証手順は[テスト基盤](../compiler/tests/README.md)の`test.arena-fuzz`を参照すること。生成テストとASanによる確認は検査の穴を探す手段であり、見つからなかったことだけで寿命検査全体の正しさを証明するものではない。
