# PRの作業手順

作業PRの手順を定める。イシューの書き方は[開発への参加](../CONTRIBUTING.md)、ソースの変更・検証は[ソースの開発規約](development.md)、リリース準備と公開は[リリース手順](releasing.md)を参照する。

## PRの種類

| 種類 | 取り込み先 | 内容 |
|---|---|---|
| 作業PR | `release/*` またはスタックの直下のブランチ | イシューに対応する変更 |
| リリース準備PR | `release/*` またはスタックの直下のブランチ | バージョンと変更履歴の確定 |
| リリースPR | `main` | リリースブランチの取り込みと公開準備 |

## イシューとPR本文

[PRテンプレート](../.github/PULL_REQUEST_TEMPLATE.md)を使う。

1つの作業PRは1つのイシューに対応させ、対応するイシューを関連付ける。イシューに紐づく作業PRが作成された後は、イシューを更新しない。イシューの記載に矛盾があれば、該当箇所と訂正内容をPR本文に記載する。その後の決定や範囲の変更、実装STEPの追加・変更もPR本文に反映し、コメントだけに残さない。

実装STEPがある場合はPR本文にチェックボックスで記載し、各STEPの完了条件を満たしたらチェックを付ける。

## 作業ブランチ

作業ブランチは、取り込み先のリリースブランチの最新状態から作成する。ブランチ保護は[リリース手順](releasing.md#ブランチ保護)を参照する。

## コミットとレビュー対応

レビューで見つかった変更は、対象のイシューと関係するものだけをそのPRで扱う。無関係な運用変更や別の問題は独立した作業PRに分ける。

コミットメッセージは、`docs:` などの接頭辞に続く説明を日本語で書く。

実装STEPとコミットの対応は[開発への参加](../CONTRIBUTING.md#実装step)に従う。レビュー対応は追加のレビューコミットとして残す。

作業PRをマージする時にsquashし、1つの作業PRを1つの意味のあるコミットにまとめる。人間が変更全体とレビュー対応を確認してからマージする。リリースブランチへ取り込んだ履歴は書き換えない。

イシューのクローズは[リリース手順](releasing.md#全体の検査とレビュー)に従う。

## 作業PRのスタック

同じリリースに取り込む作業PRは、すべて1つのGitHubスタックで管理する。
