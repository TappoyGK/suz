# PRの作業手順

イシューの書き方とPR作成前の更新方法は[開発への参加](../CONTRIBUTING.md)、ソースの変更・検証は[ソースの開発規約](development.md)に従う。リリースブランチの作成と公開は[リリース手順](releasing.md)で扱う。

## PRの種類

| 種類 | 取り込み先 | 内容 |
|---|---|---|
| 作業PR | `release/*` またはスタックの直下のブランチ | イシューに対応する変更 |
| リリース準備PR | `release/*` またはスタックの直下のブランチ | バージョンと変更履歴の確定 |
| リリースPR | `main` | リリースブランチの取り込みと公開準備 |

本文書は作業PRの手順を定める。リリース準備PRとリリースPRは[リリース手順](releasing.md)に従い、共通の操作は同文書から参照する。

## イシューとPR本文

[PRテンプレート](../.github/PULL_REQUEST_TEMPLATE.md)を使う。

作業PRには対応するイシューを関連付ける。イシューに紐づく作業PRが作成された後は、イシューを更新しない。イシューの記載に矛盾があれば、対象のイシュー、該当箇所と訂正内容をPR本文に記載する。その後の決定や範囲の変更、実装STEPの追加・変更もPR本文に反映し、コメントだけに残さない。

PR本文の実装STEPはイシューごとに分けてチェックボックスで記載し、各STEPの完了条件を満たしたらチェックを付ける。

## 作業ブランチ

作業ブランチは、最新の取り込み先のリリースブランチから作成する。取り込み先の保護は[リリース手順](releasing.md#ブランチ保護)に従う。

## 仕様・実装・検証の照合

変更規則を、言語仕様・ランタイム仕様・ツール仕様と照合する。それぞれの規則について、実装と検証箇所を確認する。言語の振る舞いは仕様例集、環境層やメモリ管理はランタイム検証、引数や出力ファイルはCLI検証で確認する。既存の検証で確認できない振る舞いは、適切な検証先に追加する。

追加仕様を別文書にまとめた場合は、規則と例を正式な仕様・例集へ移し、検証を継続して実行できる状態にする。一時文書を削除しても、仕様や検証の根拠が失われないことを確認する。

仕様書と例集は、そのコミットの仕様を表す。表題や本文に現在のリリース番号を埋め込まず、過去の仕様はGitのリリースタグから参照する。

## コミットとレビュー対応

作業PRは、単独でレビューできる変更単位にする。仕様・実装・テストと、それに必要な文書を含め、バージョンと変更履歴の確定はリリース準備で行う。

レビューで見つかった変更も、対象のイシューと関係するものだけをそのPRで扱う。無関係な運用変更や別の問題は独立した作業PRに分ける。

PRを作成する前に、差分が単独でレビューできる内容になっていることを確認する。コミットメッセージは、`docs:` などの接頭辞に続く説明を日本語で書く。

実装STEPとコミットの対応は[開発への参加](../CONTRIBUTING.md#完了条件と実装step)に従う。レビュー対応は追加のレビューコミットとして残し、PR本文の対象STEPにそのコミットを記載する。既存コミットへのamendやsquashは行わず、レビュー後に何を直したかを差分で追える状態にする。スタックの下段を反映するためのrebaseでは、各レビューコミットの内容と区切りを維持する。

作業PRをマージする時にsquashし、1つの作業PRを1つの意味のあるコミットにまとめる。人間が変更全体とレビュー対応を確認してからマージする。リリースブランチへ取り込んだ履歴は書き換えない。

独立した作業ブランチをpushし、`release/vVERSION` 向けのPRを作成する。CIの結果と差分は人間が確認し、レビュー後にマージする。CIの成功だけでは自動マージしない。

リリースブランチ向けPRではGitHubの自動クローズを前提にしない。イシューのクローズは[リリース手順](releasing.md#全体の検査とレビュー)に従う。

## 作業PRのスタック

同じリリースに取り込む作業PRは、すべて1つのGitHubスタックで管理する。スタックの基点を `release/vVERSION` とし、Markdownファイルのみを変更するPR、それ以外のPR、リリース準備PRの順に積む。Markdownのみかどうかは、そのPR自身の変更ファイルで判断する。同じ区分では基本ルールの変更を先に置き、依存する変更は依存先より後に置く。main向けのリリースPRはこのスタックに含めない。

GitHub CLIの公式拡張 `github/gh-stack` を使う。既存のブランチを採用する場合は、各ブランチを直下のブランチの上へ載せ替え、下から順に指定する。

```sh
gh extension install github/gh-stack
gh stack init --base release/vVERSION rules changes prepare
gh stack submit
```

リリース準備のPRは最後に置く。途中に作業を追加する場合は `gh stack modify` で準備PRの前にブランチを挿入し、`gh stack submit` でpushとPRの関連付けを更新する。下段を修正した場合は `gh stack rebase` と `gh stack push` で上段にも反映する。スタック内の各PRは、直下のブランチとの差分としてレビューする。

PRの作成・追加・更新時と、下段のPRがマージされた後は、公開中のPR一覧とスタックを照合し、次を確認する。

- 同じリリースに取り込む作業PRが、ドラフトや運用変更のPRも含めて、すべてスタックに入っている。
- Markdownファイルのみを変更するPRを、それ以外のPRより先に置いている。同じ区分では基本ルールの変更と依存関係に従って並べている。リリース準備のPRは最後に置いている。
- 最下段の作業PRはリリースブランチを、それ以外は直下の未マージの作業ブランチを取り込み先にしている。各PRの差分には、そのPRの変更だけが含まれている。
- GitHub上のスタックの順序・取り込み先と、ローカルのブランチの親子関係・スタック情報が一致している。

PRを作成しただけで作業を終えず、スタックへの組み込みと順序の確認まで行う。下段のマージ後は `gh stack sync` で同期する。載せ替えによって公開済みの履歴を更新する場合は、その理由を伝え、`--force-with-lease` を使う。レビューコミットは載せ替え時にもまとめない。

スタックの保護ルールとCIは、その基点に従う。ワークフローのジョブ判定でも `github.event.pull_request.stack.base.ref` を使い、スタック外では通常のPRのマージ先を使う。CIの結果確認とマージは人間が行う。

## CIの確認

レビューには実装STEPを1つずつ回しても、複数まとめて回してもよい。各実装コミットのローカル検証は[開発への参加](../CONTRIBUTING.md#完了条件と実装step)に従い、レビューに回す時点の最新コミットでCIの結果を確認する。レビューコミットのローカル検証は[ソースの開発規約](development.md#整形リント確認)に従い、最新コミットのCIも確認する。最新コミットのCI成功を、途中の実装コミットでもCIを実行したこととして扱わない。

作業PRから `release/*` への取り込みでは、`work checks` で書式、Clippy、rustdoc、通常テストを検査する。

作業ブランチへのpushではCIを起動せず、PRの検査と重複させない。全検査の手動実行は[リリース手順](releasing.md#ciの実行条件)に従う。

Markdown文書だけの変更では、変更ファイルの判定だけを行い、ビルド・テスト・配布物の生成を省略する。ただし、検証に使う `README.md`、`docs/spec.md`、`docs/spec-cases.md`、`docs/spec-cases/` 配下と、バイナリに埋め込む `runtime/third_party/ryu/README.md` の変更では検査を実行する。変更の判定に失敗した場合は必須チェックを失敗させる。

コミットを履歴から削除すると、CIが変更前のコードを取得できず、変更したファイルを調べられない場合がある。この場合は、文書だけの変更か判断できないため、検査を省略せず実行する。現在のコードを取得できない場合や、ほかの理由で変更ファイルの判定に失敗した場合は、CIを失敗にする。

ワークフロー全体はパス条件で省略せず、必須チェックのジョブを条件付きで省略する。これにより、文書だけのPRでも必須チェックが未完了のまま残らない。新たに文書をビルドや検証の入力にする場合は、`scripts/ci-changes.py` の判定とテストも更新する。

検査を実行する場合は、検査対象を絞る設定は使わない。CIの実行環境はワークフローで定め、OS・Rust・Clang・SDKのバージョンを実行ログで確認する。対応環境は[ツール仕様](tool.md)で管理する。
