# 仕様の執筆・レビュー基準

言語の目的は[言語仕様](spec.md)を正本とする。この文書は、その保証を欠落させずに仕様を記述・整理するための基準である。

## 1. 時間と資源の保証

[execution.time-resources](spec.md)に従い、時間と資源について保証する範囲・保証しない範囲を読み分けられるように書く。以下は、その原則を文書へ反映するときの区分と確認事項である。

操作と条件の組ごとに、冒頭へ次のどちらかの定型文を置く。

- **処理量の上限を保証する。**
- **処理量の上限を保証しない。**

対象の処理の一部でも上限を保証しない場合、結論は「保証しない」とする。その下に次の4項目の表を置く。内部処理の計算量が分かっていても、外部処理を含む全体の結論を説明の途中で変えない。

| 項目 | 書く内容 |
|---|---|
| 対象・条件 | 操作、適用条件、含める処理と別に扱う処理 |
| 内部の計算量 | 最悪時の計算量と変数の意味。動的確保や作業領域の有無 |
| 外部処理 | 環境層や外部APIを呼ぶ条件・回数、同期・待機の有無 |
| 利用者の制御 | 処理を避ける方法や設定。言語仕様では設定の概念を書き、CLIとの対応はツール仕様を参照する |

記述の欠落を「保証しない」という決定の代わりにしない。対象と条件を確認して結論を書く。

上限を保証しないことは、値・型安全性・寿命・失敗条件まで未定義にすることではない。「実装依存」の一語で説明を省かない。

関係する操作について、処理量が何に依存するか、確保・回収・コピー・走査・同期・待機がいつ起きるか、利用者が何を設定できるか、上限に達すると何が起きるかを書く。各規則に同じ表を繰り返さず、共通の保証を参照する。

最悪時・平均・償却の保証は区別する。O(1)だけで一定の時間内に完了するとは約束しない。測定値には環境・入力・ビルド条件を添え、保証値と区別する。この基準は新たなベンチマークの実施義務を設けない。未確認の上限や比例関係を推測で保証しない。

## 2. 正本を置く場所

| 内容 | 正本 |
|---|---|
| 文法・型・評価・失敗条件、言語の操作に伴う時間と資源の保証 | [言語仕様](spec.md) |
| CLI、検査を行うコマンド、計測機能の条件・出力・時間と資源への影響 | [ツール仕様](tool.md) |
| 保証を実現する生成C・ランタイム・環境層の実装契約 | [ランタイム仕様](runtime.md) |
| 受理・拒否・実行結果の具体例 | [仕様例集](spec-cases.md) |
| コンパイラAPI・開発方法 | [コンパイラの説明](../compiler/README.md) |
| テストの実行方法・検証手順 | [テスト基盤](../compiler/tests/README.md) |
| 設計の理由・経緯 | [設計記録](design.md) |

配置は規則名や「生成」「確保」などの単語だけで決めず、次の順に判断する。

1. **ソース構文の意味を先に判断する。** `log`や`ignore`などの動作は言語仕様に置き、有効化の条件を設定の概念で表す。CLIオプションとの対応はツール仕様へ分ける。
2. **ソースに現れない追加機能かを判断する。** 計測などを有効にしたときだけ存在する機能の契約はツール仕様に置く。ソースの受理条件と、どのコマンドで検査するかも分ける。
3. **保証と手法を分ける。** 値・制御・失敗に加え、時間・資源の保証を確認する。例えば「動的確保しない」は利用者への保証、「固定長のC配列を使う」は手法である。前者を実装詳細として隠さない。

一つの段落に複数の契約があれば分割する。共通の保証は一か所で定義し、他から参照する。上限を保証しない場合も、利用者の判断に必要な発生条件・依存要因は機能の正本へ、現実装の技術的な根拠はランタイム仕様へ置く。現在の実装方法を、今後も要求する理由なく規範にしない。

**計測機能固有のパニックの例外**：失敗条件の正本はツール仕様に置く。言語仕様にはパニック診断IDの入口だけを置き、正本を参照する。入口に条件を追加したり、同じ条件を二重定義したりしない。共通のパニック動作は言語仕様に従う。

## 3. 規範・要約・理由・例

- 規範は、適用条件、要求・許可・禁止、結果、必要な失敗条件と診断位置を確認できる文章にする。一つの規則IDで一つのまとまった契約を指し、文ごとにIDを増やさない。
- 一覧や各節には短い要約と正本への参照を残せる。理由や例も残せるが、そこだけに制約や例外を定めない。
- 網羅一覧としての定義は正本に集める。他の箇所の代表例は「例えば」「など」で示す。
- 本文と文法の双方が規範なら、両方を満たすように維持する。矛盾を便宜的な優先順位で隠さない。
- 現行仕様は現在形で書く。「従来の」「既存の」に頼らず対象を明記する。将来計画や廃止構文の経緯は分ける。

## 4. 規則IDと参照

| 接頭辞 | 定義する文書と役割 |
|---|---|
| `rt.` | 言語仕様：実行時の意味・検査・パニック診断 |
| `runtime.` | ランタイム仕様：実装の契約 |
| `tool.` | ツール仕様：コマンドと追加機能の契約 |
| `test.` | テスト基盤：検証の契約 |
| 上記以外（`src.`・`type.`・`arena.`など） | 言語仕様：各分野の言語の契約 |

契約の配置を決めてから、その役割に合うIDを付ける。パニック診断IDは`rt.`とするが、`rt.`をパニックする規則だけに限定しない。`error.*`と`err.*`などの接頭辞を見た目のために全面統一しない。

IDは章番号から独立させ、章の移動だけでは改名しない。意味の誤認を避けるなどの理由がある場合だけ改名し、旧IDを別の意味に使い回さない。移動・統合・改名時は旧IDと移動先の対応、診断への影響をPRに記載し、参照・診断・例集・検証処理を一緒に直す。

上表で掲載文書が分かる参照は規則IDで示せる。他の文書への参照は必要なリンクを付け、読者が定義へ辿れるようにする。

## 5. 編集と仕様変更の区別

配置・表現の整理では、受理するプログラム、評価結果、失敗条件、既定値、出力、時間・資源の保証を変えない。

| 不一致 | 扱い |
|---|---|
| 一覧への追加漏れで、規則と実装は一致する | 一覧を直す |
| 規則は明確だが実装が異なる | 規則を維持し、実装の不具合を別途扱う |
| 規則同士が矛盾し、意図を確定できない | 仕様判断として議論する |

既存文書にある時間・資源の保証の移動と、新しい上限を約束する変更を区別する。未確定事項は別途管理し、文書整理で保証を発明しない。

## 6. 確認

機械的な整合と意味の保持を分けて確認する。次は確認項目であり、すべての検査を自動化済みという意味ではない。

**機械で確認する項目**

- 規則IDの書式・一意性・参照先の存在、上表の接頭辞と掲載文書の対応。章番号を条件にしない。
- 診断・例集・検証処理で使うIDと、パニック診断の`rt.`制約。
- ファイル・節リンク、本文中の節番号、例集の目次と件数の整合。

**人が確認する項目**

- 正本の配置、規範と要約・理由・例の区別。
- 移動前後の条件・例外・診断位置、時間と資源の保証の保持。
- 本文と文法の意味的な整合、網羅一覧の漏れ、意図しない仕様変更。
- 「従来の」「既存の」など、変更経緯に依存する表現の混入。

テストの成功だけでは意味の保持を証明できない。例集との対応は、読める例・振る舞いを検証するテスト・未整備の範囲を区別し、IDの引用率を検証の網羅率と呼ばない。
