# Suz 実装規則

## 1. 対象

この文書は、Suzのコンパイラとランタイムの実装と、その保守性をレビューする際の基準を定める。言語の動作は[言語仕様](spec.md)、実行環境の契約は[ランタイム仕様](runtime.md)、コマンドの動作は[ツール仕様](tool.md)に従う。

**[impl.document]** 実装規則はこの文書に置く。各規則に `[impl.名前]` のIDを付け、守るべき内容、その理由、具体例を記す。[文書目録](README.md)から参照できるようにする。

理由：実装とレビューが同じ基準を参照できるようにする。

例：判定の重複を指摘するときは、[impl.rule-site] と重複している条件を示す。

## 2. モジュールの責任

### 2.1 依存の方向

**[impl.layers]** 処理を実行するモジュールと、処理の間で受け渡すデータ型を定義するモジュールを分ける。処理モジュールの依存関係は、次の階層に従う。

| 階層 | 処理モジュール | 出力 |
|---|---|---|
| 1 | `lexer` | トークン |
| 2 | `parser` | AST（`ast`） |
| 3 | `check` | IR（`check::ir`） |
| 4 | `warnings`、`codegen` | 警告、Cのソース |
| 5 | `cli` | — |

処理モジュールは、下位の階層の処理モジュールと、自分と同じ階層までで作られるデータ型を参照できる。上位の階層や、同じ階層の別の処理モジュールは参照しない。データ型を定義するモジュールは、処理モジュールを参照しない。`numeric` などの共通モジュールは、処理モジュールにも、処理の間で受け渡すデータ型のモジュールにも依存しない。ここで、番号が小さい方を下位とする。

理由：構文やデータ型の定義が、後段の検査・生成方法に依存することを防ぐ。

例：`parser` は `ast::Program` を構築してよい。`ast` から `check` を呼び出してはならない。`warnings` と `codegen` は互いを参照しない。

### 2.2 言語の規則とツールの設定

**[impl.policy-stage]** 言語仕様への適合を検査する処理と、ツールの設定に従って診断を出す処理を分ける。言語の検査ではツールの設定を受け取らず、検査を通過したプログラムが言語仕様を満たすことを保証する。診断の処理では、言語の検査で得た警告候補の位置などを受け取り、設定に従って警告・エラーとして報告するかを決める。言語仕様への適合を再検査しない。

理由：診断設定によって、言語仕様への適合の判定が変わることを防ぐ。

例：`allow` の入れ子や未使用の指定は言語の検査で判定する。整数演算の警告候補を `--deny-unhandled-arithmetic` によってエラーにするかどうかは、診断設定を適用するときに決める。

### 2.3 各処理の検査対象

**[impl.layer-errors]** 各処理が検査する対象を、次のとおり定める。

| 処理 | 検査対象 | 規則の例 |
|---|---|---|
| 入口（`lib.rs`） | ソースが正しいUTF-8であり、改行の規則を満たすこと | `src.encoding`、`src.newline` |
| `lexer` | 文字の並びがトークンの規則を満たすこと | `lit.integer`、`lit.float`、`char.literal`、`symbol.escape`、`symbol.template` |
| `parser` | トークンの並びがEBNFの文法に適合すること | `syntax.grammar`、`src.list-comma`、`src.statement-end`、`expr.comparison-chain` |
| `check` | 名前・型・値・文脈に基づく、そのほかの言語仕様への適合 | `decl.*`、`name.*`、`type.*`、`arith.*`、`struct.*`、`allow.unused`、`allow.nested` |
| 診断設定の適用 | 設定に従って診断候補を報告するかどうか | `diagnostic.*` |
| `codegen` | IRからCを生成する。Suzソースの誤りは検査しない | — |
| `cli` | コマンドの使い方と外部環境 | `tool.*` |

規則が文法に関係していても、宣言された名前・型・値を参照して決まる条件は `check` で判定する。1つの規則に含まれる別々の条件を、複数の処理に分けて判定してよい。仕様の規則を分けるかは、ファイル配置ではなく規則の内容で決める。各条件を適切な処理で判定しているかは、コードを読んでレビューで確認する。

理由：条件の判定を、必要な情報が揃う処理に置く。

例：構造体リテラルの括弧や区切りは `parser`、指定したフィールドが宣言に存在するかは `check` で判定する。

## 3. 判定とデータの定義

**[impl.rule-site]** 仕様の規則が定める条件ごとに、成否を判定する処理を1か所に置く。同じ条件の判定を別の箇所に重複して書かない。1つの規則に含まれる別々の条件は、別々の箇所で判定してよい。判定箇所のコメントに、規則IDと、その箇所で判定する条件を記す。関数全体の説明は関数の直前に `///` で書き、関数内の個別の判定の説明は `//` で書く。

診断を作る箇所（`diagnostic!`、`Diagnostic::new`）には規則IDを文字列で渡し、上記のコメントに規則IDと条件の説明を書く。このことをテストで確認する。判定する処理が [impl.layer-errors] に従っているか、同じ条件の判定が重複していないかは、レビューでコードを読んで確認する。条件の説明文を識別子として扱わず、文章の一致では重複を判断しない。

理由：条件を変更した際に、一部の実装だけが更新され、判定結果が食い違うことを防ぐ。

例：同じ変換条件を通常検査と汎用検査の双方で使う場合、共通の判定処理を呼ぶ。

宣言の重複を調べる関数に付けるrustdocの例である。

```rust
/// [decl.duplicate] トップレベルの宣言に名前の重複がないことを確認する。
```

**[impl.tree-children]** ASTとIRの各ノードが持つ子ノードとその順序は、それぞれ `ast/visit.rs` と `check/ir.rs` の1か所で定義する。すべての子ノードを同じように扱う走査・書き換え・集計・検索は、この定義を使う。評価順序やノードの意味に応じた処理は、ノードの種類ごとに書いてよい。ノードの種類を増やしたときは、子ノードの定義と、種類ごとに記述した処理を更新する。

理由：共通の走査処理の更新漏れを防ぎつつ、ノード固有の処理を書けるようにする。

例：すべての変数参照を集める走査は共通の定義を使う。短絡評価、Cの生成、値の範囲の見積もりは、ノードの種類ごとの処理として定義してよい。

**[impl.encoding]** 値の符号化、並び順、対応表は1つのモジュールで定める。逆変換も同じモジュールに置き、変換後に逆変換すると元の値に戻ることを単体テストで確認する。

理由：値を符号化する処理と復元する処理の対応を保つ。

例：整数型・浮動小数点型の組み合わせから添字を求める処理と、添字からその組み合わせを取り出す処理を同じモジュールに置く。

**[impl.diagnostic]** コンパイラの診断は、規則IDと文面を別の引数で渡して作り、別々に保存する。文面に `[規則ID]` を埋め込まない。診断を表示する際に、末尾へ `[規則ID]` を付ける。文面から規則IDを取り出したり、診断の規則IDや文面によってコンパイラの判定処理を分岐したりしない。同じ規則・同じ文面の診断は1か所で作る。テストで規則を確認するときは `rule()` を使う。

`allow` の規則名と警告の規則を照合する処理など、規則ID自体が言語やツールの入力として意味を持つ比較は認める。生成Cの実行時パニックや `#error` の文字列は、C側で表示するため、この規則の対象外とする。`diagnostic!` と `Diagnostic::new` に渡す文面への規則IDの埋め込みはテストで検出する。規則IDによる分岐の適切さはレビューで確認する。

理由：診断文の変更が判定処理を変えないようにする。

例：次のように診断を作る。`message()` は文面だけ、`rule()` は規則IDだけを返す。`Display` は位置・文面・規則IDを合わせて表示する。

```rust
crate::diagnostic!("text.slice-handler", "text extraction requires or")
```

## 4. ファイルと書式

**[impl.file-length]** `compiler/` のRustファイルと、`runtime/` のCファイル（`.c`・`.h`）は、1ファイルあたりのコード行数を500行以下とする。ファイル内のテストも数える。文書と第三者のコード（`runtime/third_party/`）は対象外とする。

行数は検査用のテストで数える。空行、`//` で始まるコメントだけの行、`/* ... */` のコメントだけの行は除く。コードとコメントが同じ行にある場合はコード行として数える。上限を超える場合は概念ごとに分割し、単に前半・後半という分け方をしない。分割によって内容のまとまりが失われる場合は、[impl.exceptions] に従い、ファイルごとの上限と理由を例外一覧に記す。

理由：コメントの削除や機械的な分割で上限を回避せず、まとまりを保って読める大きさにする。

例：定数評価と文字列の解析が同じファイルにある場合、責任ごとに分ける。単一の対応表を途中で分けることが不自然なら、そのファイルの上限について例外を決める。

**[impl.format]** Rustは `rustfmt` の既定設定で整形し、`rustfmt.toml` で行幅などを変更しない。CIで `cargo fmt --all -- --check` を実行する。`#[rustfmt::skip]` は通常の整形では読みにくくなる表などに限り、直前のコメントに理由を書く。理由のない指定はテストで検出する。

行数を減らすためだけにマクロを導入しない。マクロは、同じ形の定義を並べるために使う。`rustfmt` が整形しないマクロ本体は、手作業で既定の書式に合わせ、そのことをマクロの前にコメントで記す。第三者のコードを除く `runtime/` のCは、リポジトリの `.clang-format` で整形する。CIではバージョンを固定した `clang-format` を使い、`clang-format --dry-run --Werror` を実行する。

理由：行数の上限を整形方法の違いで回避せず、書式を一定にする。

例：子ノードの読み取りと書き換えに使う走査処理を同じマクロから定義することは認める。無関係な処理をマクロに移して行数だけを減らすことは認めない。

## 5. 前提と失敗の扱い

**[impl.invariant]** 成立しない場合に、誤ったCコードの生成、誤った診断、仕様違反の見逃しにつながる前提は、`debug_assert!` またはテストで確認する。コメントだけを根拠にしない。どの前提がこの規則に該当するかはレビューで判断する。

理由：後段の処理が依存する前提が成立しなくなったことを検出する。

例：派生した構造体の定数キャッシュが具体型だけを持つ前提を、キャッシュの生成時に検査する。

**[impl.no-silent]** `Err` や、失敗を表す `None` を理由なく捨てない。失敗を捨てる場合は、言語・ツールの規則ID、または [impl.invariant] に従って確認する前提を根拠として示す。

CIではClippyの次のリントを適用する。例外には `#[allow(clippy::名前, reason = "理由")]` で理由を書く。既存コードの違反は [impl.exceptions] の例外一覧でも管理できる。`.ok()?` などを使い、失敗をエラーとして報告せず「この処理の対象ではない」として扱うことが適切かどうかは、レビューで確認する。

| リント | 対象 |
|---|---|
| `let_underscore_must_use` | `let _ =` による結果の破棄 |
| `unused_result_ok` | 文として書いた `.ok();` |
| `map_err_ignore` | `map_err` で元のエラーを捨てる処理 |

理由：条件に合わないだけの場合と、エラーとして報告すべき失敗を区別する。

例：最適化のための定数評価に失敗して通常の実行へ戻る場合は、その扱いを認める規則または検証済みの前提を示す。

## 6. テストと用語

**[impl.spec-case]** 仕様の規則ごとに、その規則を主根拠とする仕様例を1つ以上置く。仕様例の入出力で確認できない規則は、[仕様例集](spec-cases.md)に検証先の内部テストを記す。

理由：各規則と、継続して実行する検証の対応を明らかにする。

例：生成される関数の数や、同じ具体型に対して生成した関数が再利用されることは、内部表現のテストで確認する。仕様例集には、そのテストの参照先を記す。

**[impl.regression]** 不具合を修正するときは、その不具合を再現するテストを加える。テスト名または注記に、根拠となる規則IDを書く。

理由：修正した振る舞いが失われたときに検出できるようにする。

例：整数型と浮動小数点型を候補に持つ汎用関数を、誤って拒否する不具合を修正する。この場合、具体型で書いた関数と受理・拒否の結果が一致することをテストし、その注記に `[num.fn-body]` を記す。

**[impl.terms]** 仕様の用語とコードの名前は次の対応を使う。1つの概念には1つの名前を使い、表にない概念に名前を付けるときは、この表に追加する。

| 仕様の用語 | コードの名前 |
|---|---|
| 汎用関数 | `generic`、関数を指す名前は `generic_function` |
| 汎用検査 | 型名は `GenericCheck`、関数などの名前は `generic_check` |
| 保留した判定 | 型名は `Deferred`、値などの名前は `deferred` |
| 具体型 | `concrete` |

理由：仕様と実装で同じ概念を追えるようにする。

例：具体型を示す名前には `concrete` を使い、同じ概念に別の呼び名を増やさない。

## 7. ドキュメント

**[impl.crate-doc]** `compiler/src/lib.rs` の先頭の `//!` に処理の流れを書く。各処理のモジュールと、処理の間で受け渡す型にはrustdocの内部リンクを張る。

理由：入口から実装の責任とデータの流れをたどれるようにする。

例：

```rust
//! Suzコンパイラ。
//!
//! 1. [`lexer`]：文字列をトークンに分ける。
//! 2. [`parser`]：トークンから [`ast::Program`] を構築する。
//! 3. [`check`]：言語の規則を検査し、[`check::ir::CheckedProgram`] を作る。
//! 4. [`warnings`]：警告候補にツールの設定を適用する。
//! 5. [`codegen`]：IRからCを生成する。
```

**[impl.module-doc]** `compiler/src` のテストを除く各ファイルの先頭に、`//!` でモジュールの役割、処理上の位置付け、検査する仕様の規則ID、呼び出す側のモジュールへのリンクを書く。仕様の検査を行わないモジュールには規則IDを要求しない。先頭に `//!` があることをテストで確認する。

理由：そのファイルの責任と利用箇所を、実装を読み始める前に確認できるようにする。

例：

```rust
//! 意味検査で、代入の右辺への制約 [assign.rhs-write] を検査する。
//! 代入の右辺で、外側の代入先と重なる場所への書き込みがないことを確認する。
//!
//! [`super::statements`] から代入ごとに呼ばれる。
```

**[impl.type-doc]** ASTとIRの型には `///` で説明を書く。IRの説明には、対応するASTの型へのリンクを記し、ASTの検査によって新たに確定した情報を説明する。

理由：型が保持する情報と、後段が前提にできることを明らかにする。

例：検査済みの式を表すIRの型には、対応するASTの型へのリンクを記す。さらに、式の型・参照先の宣言番号・値の範囲など、検査で確定した情報を説明する。

**[impl.doc-examples]** ドキュメントにSuzのコード例を書く場合は、コードブロックの言語を `suz` にする。

理由：Suzの例をRustのコードとして検査させない。

例：

```suz
fn main() -> u8 { return 0 }
```

**[impl.doc-language]** コード内のコメント、rustdoc、Markdown文書は日本語の常体で書く。コマンドが利用者に表示するメッセージは英語とする。コンパイラの診断、ツールのメッセージ、実行時の診断もこれに含む。識別子、規則ID、外部APIの名前は元の表記を使う。第三者のコードは翻訳の対象外とする。

理由：意図と前提を日本語で説明し、コマンドの出力言語を一定にする。

例：理由を示すコメントは「具体型が決まるまで判定を保留する」と書き、利用者向けの診断は英語で記述する。

**[impl.doc-check]** CIで `RUSTDOCFLAGS="-D warnings" cargo doc --no-deps --document-private-items` を実行する。

理由：公開範囲が限定された内部実装も文書化し、リンク切れなどを検出する。

例：型名を変更した後に古いrustdocリンクが残った場合、警告をエラーとして検出する。

## 8. コミットとレビュー

**[impl.commit]** 1つのコミットには1つの目的の変更を入れる。動作を変える場合、または以前の変更を取り消す場合は、コミットメッセージの本文に変更内容と理由を書く。

理由：変更の目的と、動作が変わる根拠を履歴から追えるようにする。

例：派生キャッシュを定数判定の対象から外した場合、その変更と理由をコミット本文に記す。

**[impl.review]** 保守性の指摘には、反している `[impl.*]` の規則IDを示す。該当する規則がない問題は、コードの違反として指摘せず、規則の追加を提案する。適用される規則を満たすコードには、保守性の違反を指摘しない。

理由：指摘と、修正後に満たすべき条件を対応させる。

例：共通の条件を2か所で判定している場合、[impl.rule-site] と対象の判定箇所を示す。

**[impl.review-gap]** 規則に定めのない問題が見つかっても、規則を追加するかどうかの検討を理由に、そのPRのマージを止めない。追加した規則は、それ以降にレビューを開始するPRから適用する。

理由：新しい基準の合意と、既に合意した基準によるレビューを分ける。

例：規則に定めのないファイル配置の問題を見つけた場合、そのPRの修正要求にせず、規則を追加する提案として扱う。

**[impl.review-scope]** 規則はPRで追加・変更した部分に適用する。変更と無関係な既存コードの違反は、そのPRでの修正を求めない。既存コードの違反は [impl.exceptions] に従って例外一覧に記録し、解消するためのPRを別途作る。

理由：各PRの目的と修正範囲を限定する。

例：新しい関数の変更と無関係な既存ファイルの行数超過は、そのPRの修正要求に含めない。

**[impl.review-fixed]** PRに適用する規則は、レビュー開始時点のこの文書で固定する。レビュー中に規則を追加・変更しても、そのPRの合格条件を増やさない。

理由：レビュー中に合格条件が変わり続けることを防ぐ。

例：レビュー中に行数の上限が変更されても、そのPRではレビュー開始時点の上限を使う。


**[impl.exceptions]** 実装規則の例外は、`compiler/tests/implementation-exceptions.toml` にまとめる。1件を `[[exceptions]]` で記述し、次の項目を持たせる。

| 項目 | 内容 |
|---|---|
| `rule` | 対象の実装規則ID。角括弧を付けない |
| `path` | 対象ファイルのリポジトリルートからの相対パス |
| `reason` | 例外として認める理由 |
| `item` | 対象を限定する必要がある場合の、関数名・型名などの識別情報 |
| `max_code_lines` | `impl.file-length` の例外で認めるコード行数の上限。この規則の例外では必須 |

`rule`、`path`、`reason` はすべての例外に必須とする。既存コードの違反を記録する場合も同じ形式を使う。例外の追加や適用範囲の拡大は、理由と対象をPRに明記し、人間の合意を得る。既存コードの違反の記録も、この手続きを省略しない。個別のコードへの修正要求と、例外を認めるかどうかの判断を分ける。

例外を解消した場合は、その修正PRで対応する記録を削除する。対象を一部だけ修正した場合は、記録の適用範囲を残った部分に限定する。行数の上限を引き下げる場合も、そのファイルが新しい上限を満たすことを確認する。

例外一覧を使うテストでは、例外を適用する前の検査結果と各記録を照合する。記録に対応する違反が現在のコードに存在しなければ、不要な例外としてテストを失敗させる。`impl.file-length` の例外では、対象ファイルのコード行数が500行以下になった場合も失敗させる。これにより、別の変更で違反が解消された場合や、記録の削除を忘れた場合も検出する。

理由：例外の対象と理由を明確にし、不要になった例外を残さないようにする。

例：次はファイルの行数に対する例外の書式を示す。パスと数値は説明用であり、この記載によって例外を認めるものではない。

```toml
[[exceptions]]
rule = "impl.file-length"
path = "compiler/src/example_table.rs"
reason = "単一の対応表であり、分割すると項目の対応を確認しにくくなるため"
max_code_lines = 550
```
