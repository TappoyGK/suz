# Suz 実装規則

## 1. 対象

この文書は、Suzのコンパイラとランタイムの実装、および保守性のレビューで使う基準を定める。言語の動作は[言語仕様](spec.md)、実行環境の契約は[ランタイム仕様](runtime.md)、コマンドの動作は[ツール仕様](tool.md)に従う。

**[impl.document]** 実装規則はこの文書に置く。各規則に `[impl.名前]` のIDを付け、規則の文、理由、例を記す。[文書目録](README.md)から参照できるようにする。

理由：実装とレビューが同じ基準を参照できるようにする。

例：判定の重複を指摘するときは、[impl.rule-site] と重複している条件を示す。

## 2. モジュールの責任

### 2.1 依存の方向

**[impl.layers]** モジュールを、処理の段と、段の間で受け渡すデータ型に分ける。

| 段 | 処理のモジュール | 作るデータ型 |
|---|---|---|
| 1 | `lexer` | トークン |
| 2 | `parser` | AST（`ast`） |
| 3 | `check` | IR（`check::ir`） |
| 4 | `warnings`、`codegen` | 警告、Cのソース |
| 5 | `cli` | — |

処理のモジュールは、番号の小さい段の処理と、自分の段までで作られるデータ型を参照できる。番号の大きい段の処理、および同じ段の別の処理モジュールを参照しない。データ型のモジュールは処理のモジュールを参照しない。`numeric` などの共通モジュールは、処理のモジュールにも、段の間で受け渡すデータ型のモジュールにも依存しない。

理由：構文やデータ型の定義が、後段の検査・生成方法に依存することを防ぐ。

例：`parser` は `ast::Program` を構築してよい。`ast` から `check` を呼び出してはならない。`warnings` と `codegen` は互いを参照しない。

### 2.2 言語の規則とツールの設定

**[impl.policy-stage]** 言語の規則を判定する処理と、ツールの設定を適用する処理を別の段に分ける。言語の規則を判定する段はツールの設定を受け取らず、その段を通ったプログラムは言語の規則を満たす。設定を適用する段は、前段が求めた警告候補の位置などを受け取り、警告・エラーとして報告するかを決める。言語の規則を判定し直さない。

理由：同じプログラムに対する言語の判定を、診断設定から独立させる。

例：`allow` の入れ子や未使用の指定は言語の検査で判定する。整数演算の警告候補を `--deny-unhandled-arithmetic` によってエラーにする処理は、設定を適用する段で行う。

### 2.3 エラーを判定する段

**[impl.layer-errors]** 各段は、次の責任に属する条件を判定する。

| 段 | 判定する条件 | 規則の例 |
|---|---|---|
| 入口（`lib.rs`） | ソースのバイト列のUTF-8と改行 | `src.encoding`、`src.newline` |
| `lexer` | 文字の並びがトークンを構成する条件 | `lit.integer`、`lit.float`、`char.literal`、`symbol.escape`、`symbol.template` |
| `parser` | トークンの並びがEBNFの文法に適合する条件 | `syntax.grammar`、`src.list-comma`、`src.statement-end`、`expr.comparison-chain` |
| `check` | 名前・型・値・文脈によって決まる、そのほかの言語の条件 | `decl.*`、`name.*`、`type.*`、`arith.*`、`struct.*`、`allow.unused`、`allow.nested` |
| 設定を適用する段 | 診断候補を設定に従って報告するか | `diagnostic.*` |
| `codegen` | IRからCを生成する。Suzソースに対するエラーを判定しない | — |
| `cli` | コマンドの使い方と外部環境 | `tool.*` |

規則が文法に関係していても、宣言された名前・型・値を参照して決まる条件は `check` で判定する。1つの規則に含まれる別々の条件を、複数の段で判定してよい。仕様の規則を分けるかは、ファイル配置ではなく規則の内容で決める。各条件と担当する段の適合性は、[impl.rule-index] の対応表とコードを使ってレビューで確認する。

理由：判定に必要な情報を持つ段が、その条件に責任を持つようにする。

例：構造体リテラルの括弧や区切りは `parser`、指定したフィールドが宣言に存在するかは `check` で判定する。

## 3. 判定とデータの定義

**[impl.rule-site]** 仕様の規則が定める条件ごとに、成否を判定する処理を1か所に置く。同じ条件の判定を別の箇所に重複して書かない。1つの規則に含まれる別々の条件は、別々の箇所で判定してよい。判定箇所には、規則IDと担当する条件をコメントで記す。

理由：同じ条件の変更が、複数の判定の更新漏れによって食い違うことを防ぐ。

例：同じ変換条件を通常検査と汎用検査の双方で使う場合、共通の判定処理を呼ぶ。コメントには担当する条件を書く。

```rust
// [decl.duplicate] トップレベルの宣言の重複を判定する。
```

**[impl.tree-children]** ASTとIRの各節の子の並びは、`ast/visit.rs` と `check/ir.rs` に1度だけ定める。すべての子を同じように扱う走査・書き換え・集計・検索は、この定義を使う。評価順序や節の意味に固有の処理は、節ごとに書いてよい。節の種類を増やしたときは、子の並びの定義と、節ごとに定義した処理を更新する。

理由：汎用的な走査の更新箇所を共有しつつ、各節の意味に必要な処理を表現できるようにする。

例：すべての変数参照を集める走査は共通の定義を使う。短絡評価、Cの生成、値の範囲の見積もりは、節ごとの処理として定義してよい。

**[impl.encoding]** 値の符号化、並び順、対応表は1つのモジュールで定める。逆変換も同じモジュールに置き、往復すると元の値に戻ることを単体テストで確認する。

理由：同じ表現を作る処理と読む処理の対応を保つ。

例：整数型・浮動小数点型の組み合わせから添字を求める処理と、添字からその組み合わせを取り出す処理を同じモジュールに置く。

**[impl.diagnostic]** コンパイラの診断は、規則IDと文面を別の引数で渡して作り、別々に保存する。文面に `[規則ID]` を埋め込まない。表示の末尾の `[規則ID]` は表示時に付ける。文面から規則IDを取り出したり、診断の規則IDや文面によってコンパイラの判定処理を分岐したりしない。同じ規則・同じ文面の診断は1か所で作る。テストで規則を確認するときは `rule()` を使う。

`allow` の規則名と警告の規則を照合する処理など、規則ID自体が言語やツールの入力として意味を持つ比較は認める。生成Cの実行時パニックや `#error` の文字列は、C側で表示するため、この規則の対象外とする。`diagnostic!` と `Diagnostic::new` に渡す文面への規則IDの埋め込みはテストで検出する。規則IDによる分岐の適切さはレビューで確認する。

理由：診断文の変更が判定処理を変えないようにする。

例：次のように診断を作る。`message()` は文面だけ、`rule()` は規則IDだけを返す。`Display` は位置・文面・規則IDを合わせて表示する。

```rust
crate::diagnostic!("text.slice-handler", "text extraction requires or")
```

## 4. ファイルと書式

**[impl.file-length]** `compiler/` のRustファイルと、`runtime/` のCファイル（`.c`・`.h`）は、1ファイルのコード行を500行以下とする。ファイル内のテストも数える。文書と第三者のコード（`runtime/third_party/`）は対象外とする。

行数は検査用のテストで数える。空行、`//` で始まるコメントだけの行、`/* ... */` のコメントだけの行は除く。コードとコメントが同じ行にある場合はコード行として数える。上限を超える場合は概念ごとに分割し、単に前半・後半という分け方をしない。概念を分けると不自然になる場合は、ファイルごとの上限と理由を例外一覧に記す。例外の追加は、規則の抜けと同様にレビューの指摘とは別に決定する。

理由：コメントの削除や機械的な分割で上限を回避せず、まとまりを保って読める大きさにする。

例：定数評価と文字列の解析が同じファイルにある場合、責任ごとに分ける。単一の対応表を途中で分けることが不自然なら、そのファイルの上限について例外を決める。

**[impl.format]** Rustは `rustfmt` の既定設定で整形し、`rustfmt.toml` で行幅などを変更しない。CIで `cargo fmt --all -- --check` を実行する。`#[rustfmt::skip]` は整形すると読みにくくなる表などに限り、直前のコメントに理由を書く。理由のない指定はテストで検出する。

行数を減らすためだけにマクロを導入しない。マクロは、同じ形の定義を並べるために使う。`rustfmt` が整形しないマクロ本体は、手で同じ書式に整え、そのことをマクロの前にコメントで記す。第三者のコードを除く `runtime/` のCは、リポジトリの `.clang-format` で整形する。CIでは固定した版の `clang-format` を使い、`clang-format --dry-run --Werror` を実行する。

理由：行数の上限を整形方法の違いで回避せず、書式を一定にする。

例：読み取り用と書き換え用の子の走査を同じマクロから定義することは認める。無関係な処理をマクロに移して行数だけを減らすことは認めない。

## 5. 前提と失敗の扱い

**[impl.invariant]** 破られると誤ったC、誤った診断、違反の見逃しにつながる前提は、`debug_assert!` またはテストで確認する。コメントだけを根拠にしない。どの前提がこの規則に該当するかはレビューで判断する。

理由：後段の処理が依存する前提の崩れを検出する。

例：派生した構造体の定数キャッシュが具体型だけを持つ前提を、キャッシュの生成時に検査する。

**[impl.no-silent]** `Err` や、失敗を表す `None` を理由なく捨てない。失敗を捨てる場合は、言語・ツールの規則ID、または [impl.invariant] に従って確認する前提を根拠として示す。

CIではClippyの次のリントを適用する。例外には `#[allow(clippy::名前, reason = "理由")]` で理由を書く。既存違反は [impl.review-scope] の例外一覧でも管理できる。失敗を「当てはまらない」として扱う `.ok()?` などの適切さはレビューで確認する。

| リント | 対象 |
|---|---|
| `let_underscore_must_use` | `let _ =` による結果の破棄 |
| `unused_result_ok` | 文として書いた `.ok();` |
| `map_err_ignore` | `map_err` で元のエラーを捨てる処理 |

理由：意図した不成立と、報告すべき失敗を区別する。

例：最適化のための定数評価に失敗して通常の実行へ戻る場合は、その扱いを認める規則または検証済みの前提を示す。

## 6. テストと用語

**[impl.spec-case]** 仕様の規則ごとに、その規則を主根拠とする仕様例を1つ以上置く。仕様例の入出力で確認できない規則は、[仕様例集](spec-cases.md)に検証先の内部テストを記す。

理由：各規則と、継続して実行する検証の対応を明らかにする。

例：生成する関数の数と同じ具体型での共有は、対応する内部表現のテストを仕様例集から参照する。

**[impl.regression]** 不具合を修正するときは、その不具合を再現するテストを加える。テスト名または注記に、根拠となる規則IDを書く。

理由：修正した振る舞いが失われたときに検出できるようにする。

例：整数と浮動小数点が混在する型候補の誤拒否を直す場合、具体型版との受理・拒否の一致を確認するテストに `[num.fn-body]` を記す。

**[impl.terms]** 仕様の用語とコードの名前は次の対応を使う。1つの概念には1つの名前を使い、表にない概念に名前を付けるときは、この表に追加する。

| 仕様の用語 | コードの名前 |
|---|---|
| 汎用関数 | `generic`、関数を指す名前は `generic_function` |
| 汎用検査 | 型名は `GenericCheck`、関数などの名前は `generic_check` |
| 保留した判定 | 型名は `Deferred`、値などの名前は `deferred` |
| 具体型 | `concrete` |

理由：仕様と実装で同じ概念を追えるようにする。

例：具体型を示す名前には `concrete` を使い、同じ概念に別の呼び名を増やさない。

## 7. ドキュメント

**[impl.crate-doc]** `compiler/src/lib.rs` の先頭の `//!` に処理の流れを書く。各段のモジュールと、段の間で受け渡す型にはrustdocの内部リンクを張る。

理由：入口から実装の責任とデータの流れをたどれるようにする。

例：

```rust
//! Suzコンパイラ。
//!
//! 1. [`lexer`]：文字列をトークンに分ける。
//! 2. [`parser`]：トークンから [`ast::Program`] を構築する。
//! 3. [`check`]：言語の規則を検査し、[`check::ir::CheckedProgram`] を作る。
//! 4. [`warnings`]：警告候補にツールの設定を適用する。
//! 5. [`codegen`]：IRからCを生成する。
```

**[impl.module-doc]** `compiler/src` のテストを除く各ファイルの先頭に、`//!` でモジュールの役割、担当する段、判定する仕様の規則ID、呼び出す側のモジュールへのリンクを書く。判定する規則がないモジュールには規則IDを要求しない。先頭に `//!` があることをテストで確認する。

理由：そのファイルの責任と利用箇所を、実装を読み始める前に確認できるようにする。

例：

```rust
//! 言語の検査の段で [assign.rhs-write] を判定する。
//! 代入の右辺が、外側の代入先と重なる場所へ書き込むことを禁じる。
//!
//! [`super::statements`] から代入ごとに呼ばれる。
```

**[impl.type-doc]** ASTとIRの型には `///` で説明を書く。IRの説明には、対応するASTの型へのリンクと、ASTに加えて確定した情報を記す。

理由：型が保持する情報と、後段が前提にできることを明らかにする。

例：検査済みの式には、元の式の型へのリンクと、式の型・参照先の宣言番号・値の範囲などの確定済み情報を説明する。

**[impl.doc-examples]** ドキュメントにSuzのコード例を書く場合は、コードブロックの言語を `suz` にする。

理由：Suzの例をRustのコードとして検査させない。

例：

```suz
fn main() -> u8 { return 0 }
```

**[impl.doc-language]** コード内のコメント、rustdoc、Markdown文書は日本語の常体で書く。コマンドが利用者に表示するメッセージは英語とする。コンパイラの診断、ツールのメッセージ、実行時の診断もこれに含む。識別子、規則ID、外部APIの名前は原表記を使う。第三者のコードは翻訳の対象外とする。

理由：意図と前提を日本語で説明し、コマンドの出力言語を一定にする。

例：理由を示すコメントは「具体型が決まるまで判定を保留する」と書き、利用者向けの診断は英語で記述する。

**[impl.doc-check]** CIで `RUSTDOCFLAGS="-D warnings" cargo doc --no-deps --document-private-items` を実行する。

理由：公開範囲が限定された内部実装も文書化し、リンク切れなどを検出する。

例：型名を変更した後に古いrustdocリンクが残った場合、警告をエラーとして検出する。

**[impl.rule-index]** 規則IDを渡して診断を作る箇所から、規則ID、判定箇所のファイルと段、[impl.rule-site] のコメントに書いた条件の説明の対応表を作る。テストでは、診断を作るすべての箇所が規則IDと条件の説明を持って対応表に載ることを確認する。

担当する段が [impl.layer-errors] に適合するかと、同じ条件を重複して判定していないかは、レビューで対応表とコードを読んで判断する。条件の説明文を識別子として使わず、説明文の一致では判断しない。

理由：診断の実装を追跡できるようにし、意味の判断と機械的な掲載確認を分ける。

例：`decl.duplicate` に複数の掲載箇所がある場合、トップレベルの宣言とローカル宣言など、担当する条件を対応表で確認する。説明を言い換えただけで別の条件とはみなさない。

## 8. コミットとレビュー

**[impl.commit]** 1つのコミットには1つの目的の変更を入れる。動作を変える場合、または以前の変更を取り消す場合は、コミットメッセージの本文に変更内容と理由を書く。

理由：変更の目的と、動作が変わる根拠を履歴から追えるようにする。

例：派生キャッシュを定数判定の対象から外した場合、その変更と理由をコミット本文に記す。

**[impl.review]** 保守性の指摘には、反している `[impl.*]` の規則IDを示す。規則IDを示せない問題はコードの違反とせず、規則の抜けとして扱う。適用される規則を満たすコードには、保守性の違反を指摘しない。

理由：指摘と、修正後に満たすべき条件を対応させる。

例：共通の条件を2か所で判定している場合、[impl.rule-site] と対象の判定箇所を示す。

**[impl.review-gap]** 規則の抜けは、規則を追加するか決めるまで、そのPRのマージを止める理由にしない。追加した規則は、それ以降にレビューを開始するPRから適用する。

理由：新しい基準の合意と、既に合意した基準によるレビューを分ける。

例：規則にない配置上の問題を見つけた場合、そのPRの修正要求にせず、規則を追加する提案として扱う。

**[impl.review-scope]** 規則はPRで追加・変更した部分に適用する。変更と無関係な既存違反を、そのPRで直す義務にしない。既存違反は例外一覧と、それを解消する整理のPRで扱う。

理由：各PRの目的と修正範囲を限定する。

例：新しい関数の変更と無関係な既存ファイルの行数超過は、そのPRの修正要求に含めない。

**[impl.review-fixed]** PRに適用する規則は、レビュー開始時点のこの文書で固定する。レビュー中に規則を追加・変更しても、そのPRの合格条件を増やさない。

理由：レビュー中に合格条件が変わり続けることを防ぐ。

例：レビュー中に行数の上限が変更されても、そのPRではレビュー開始時点の上限を使う。
