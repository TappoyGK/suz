# Suz 🛎️

Suzは、Cを生成する静的型付けのプログラミング言語である。

名前は日本語の「鈴」に由来し、「すず（Suzu）」と発音する。

## 目的

ゲームとシンセサイザーの開発に特化した言語と環境を提供する。

## 目標

次の順に優先する。

1. ゲームとシンセサイザーの開発速度を上げる。
2. 手書きのCに近い実行速度を実現する。

## メモリ管理

Suzは、`new`で確保する実体を作業領域（arena）に置き、その領域を抜けるときにまとめて回収する。個々の実体を解放する操作は書かない。

代表的な動的確保の扱いを比較すると、次のようになる。

| 項目 | C（`malloc`・`free`） | Rust（`Box`） | Suz（`new`・`arena`） |
|---|---|---|---|
| 回収の時点 | プログラマーが`free`を呼ぶとき | 所有者が破棄されるとき | 作業領域を抜けるとき |
| 意識すること | 誰が、いつ解放するか | 誰が所有し、誰が借用するか | どの作業領域に置き、いつまで使うか |

`main`は既定の作業領域を持つ。関数は呼び出された時点の作業領域へ確保し、関数内で`arena`を開いた場合は、その内側では新しい領域へ確保する。値を返すかどうかで確保先は変わらない。

```suz
fn main() -> u8 {
    fix ptr saved = new 10 // mainの終了まで保持する実体
    arena {
        fix ptr temporary = new 20
        fix total = .saved + .temporary
        log info `${total}`
    } // temporaryが指す実体を回収する
    fix value = .saved // 外側の実体は引き続き使える
    log info `${value}`
    return 0
}
```

### 解放後のメモリを使わないために

作業領域を抜けると、その中で確保した実体は使えなくなる。コンパイラは、回収後の実体を使えてしまう場所に参照を保存するコードを拒否する。

ただし、安全かどうかをコンパイラだけでは判断できない場合もある。`objection`は、コンパイラが証明できなかった参照の保存や返却について、プログラマーが安全性を保証するための構文である。また、Cの関数を呼ぶ場合は、C側が参照をいつまで使うかなど、外部APIの契約をプログラマーが確認する必要がある。詳しくは[理由付きの寿命保証](docs/spec.md#92-理由付きの寿命保証)と[安全性](docs/spec.md#12-安全性)を参照すること。

### Suzで起こり得るメモリリーク

ループの各回で確保した実体への参照が、その回の終了後には残らない場合がある。それでも作業領域をループの外に置くと、メモリは各回の終了時に回収されず、蓄積していく。コンパイラはこの場合に警告する（[arena.loop-allocation]）。詳しくは[作業領域とポインタ](docs/spec.md#9-作業領域とポインタ)を参照すること。

### 作業領域の容量設定

普段は既定の設定のままで使える。最初に64 MiBを確保し、足りなくなったら追加で確保する。

ゲームやシンセサイザーでは、処理速度に加えて、フレームや音声処理にかかる時間を安定させることも重要になる。必要な容量をあらかじめ確保しておけば、処理中にメモリを追加確保する回数を減らせる。用途に合わせた設定は、速度の改善や処理時間のばらつきの低減につながる。

容量は、ビルド時に次のオプションで指定する。

| オプション | 意味 | 既定値 |
|---|---|---|
| `--arena-initial` | 最初に確保する容量 | `64M` |
| `--arena-grow` | 追加確保する容量の基準 | `64M` |
| `--arena-limit` | 確保する総容量の上限 | `unlimited` |

追加確保を禁止すると、処理中に作業領域を拡張することがなくなる。また、コンパイラは領域の拡張を考慮する必要がなくなり、確保・回収の処理を簡略化できる。

例えば、必要な容量を実測して256 MiB以内に収まると分かっている場合は、最初から256 MiBを確保し、追加確保を禁止できる。

```sh
suz build game.suz -o game -O2 --arena-initial 256M --arena-grow 0
```

回収済みの領域は再利用できる。ただし、この設定で容量が足りなくなるとパニックするため、十分な余裕を持たせる必要がある。容量を大きくするだけで演算そのものが速くなるわけではないので、実際の処理時間とメモリ使用量を測って調整すること。

単位や上限の詳しい扱いは、[作業領域の容量](docs/tool.md#32-作業領域の容量)を参照すること。

## 導入

配布物は実行ファイル `suz` 1つである。実行権限を付け、`PATH` の通ったディレクトリに置く。

```sh
chmod +x suz
suz --version
```

対象はmacOS・Apple Siliconである。対応するOS・Cコンパイラ・SDKは[ツール仕様](docs/tool.md#1-配布と外部ツール)で定める。

プログラムのビルドと実行には、外部のClang・リンカー・macOS SDKを使う。Xcode Command Line Toolsで用意する場合は、次を実行する。

```sh
xcode-select --install
```

ソースの検査とC一式の出力には、外部ツールの用意は不要である。

## 使い方

次を `hello.suz` に保存する。

```suz
fn main() -> u8 {
    log info `Hello, Suz!`
    return 0
}
```

```sh
suz check hello.suz
suz run hello.suz
```

ログは標準エラーに出力される。

```text
info hello.suz:2: Hello, Suz!
```

実行ファイルを残す場合は `build` を使う。出力先には新規ファイルを指定する。

```sh
suz build hello.suz -o hello -O2
./hello
```

C一式を取り出す場合は、新規ディレクトリを指定する。ランタイム・環境層・Ryu・ライセンス・ビルドスクリプトも一緒に出力される。

```sh
suz emit-c hello.suz -o generated
```

コマンドとオプションは `suz --help`、`suz build --help` などで確認できる。

## 開発

イシューの書き方と更新方法は[開発への参加](CONTRIBUTING.md)を参照する。

Rustのツールチェーンは `rust-toolchain.toml` で指定する。リポジトリのルートでビルドと通常テストを実行する。

```sh
cargo build --release --locked
cargo test --locked
```

ビルドしたコマンドは `target/release/suz` に生成される。詳しい利用方法は[コンパイラ](compiler/README.md)、検証方法は[テスト基盤](compiler/tests/README.md)を参照する。
